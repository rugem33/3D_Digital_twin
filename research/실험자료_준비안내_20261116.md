# 논문 실험자료 준비 안내

현재 교정본 Ⅴ장 1~4절과 표 4~6을 기준으로 정리했다. 논문을 모두 읽지 않아도 아래 세 묶음의 원자료를 준비하면 된다. 표·그래프 계산과 결과 해석은 원자료를 받아 작성한다. 예시·빈칸은 실험 결과가 아니다.

최신 확인: 사용자는 기본 기능의 정상 동작을 이미 확인했다고 보고했다. 이 결과와 확보된 과거 오류 기록을 논문에 반영했다. 아래 기능 실행 절차는 기록 보완·재현이나 정량 평가가 필요할 때 사용하는 안내이며, 기본 기능의 확인을 처음부터 모두 다시 수행하라는 뜻은 아니다. 정상 실행 화면·빌드 정보 등 남아 있는 증거를 제공하면 보강할 수 있다. 자세한 근거는 `개발오류_및_기능확인_기록_20261116.md` 참조.

화면 판단은 내부 팀원 평가로 진행하기로 했다. 조건별 이미지와 팀원별 실제 응답을 함께 기록한다. 타 지역 시험은 새 지역 자료를 입력해 기능을 확인하고 변경 작업을 남기는 방식이다. 현재 범위를 벗어나면 해당 지역의 DEM·도로자료도 준비해야 한다.

## 1. 어떤 자료가 필요한가

| 묶음 | 논문에서 확인할 것 | 사용자가 준비할 핵심 자료 |
|---|---|---|
| 기능 실행 | GPS 위치부터 시점·목적지·경로·도착까지 연결되는가 | 실제 단말 화면 녹화, 같은 실행의 로그, 출발지·목적지와 성공·실패 기록 |
| 화면 판단 | 건물·지형·이미지 조건에서 방향·목적지 판단이 어떻게 달라지는가 | 같은 조건의 화면·영상, 사전 정답, 사람별 원응답·응답시간·설문 |
| 자료 추가·교체 | 다른 구역 자료를 기존 구조로 적용할 때 무엇이 유지·변경되는가 | 적용할 두 구역 자료, 변경 메모, 전후 화면과 기능 확인 결과 |

현재 계획에서 FPS·메모리·로딩시간은 보조 자료다. 그 성능의 개선이나 특정 목표를 주장하려는 경우에 해당 측정을 추가한다. 위 세 묶음의 자료를 우선 준비한다.

## 2. 공통 정보: 실행 때 한 번 기록

- 실험 빌드명: 논문에서 처음 시험하는 빌드는 A(0.1.0), 부분 수정 후에는 A-1(0.1.1) 등으로 구분한다.
- 날짜·장소, 실제 사용 단말의 기종·OS, 현장 실행인지 Unity 모의 입력인지 기록한다.
- 사용한 프로젝트·앱 파일과 서버를 식별할 정보를 남긴다. 해당 버전의 코드·설정이 있으면 Unity·Cesium 버전, 커밋과 설정은 제가 추출할 수 있다.
- 실제 사용 자료의 파일명·경로, 지형 작업 ID 또는 URL을 기록한다. 로컬에 존재하는 모든 자료가 아니라 실제 실행에 사용한 자료를 식별한다.
- 카메라 눈높이와 건물 높이 입력 등은 실제 적용값을 기록한다. 현재 확인 기록의 눈높이 3m와 논문 계획 2m를 임의로 혼합하지 않는다.
- 같은 빌드의 의도적인 화면 비교 조건은 조건 번호로 구분한다. 조건이 셋이라고 앱 버전을 세 개 만들어야 하는 것은 아니다. 실행 코드를 수정한 경우에는 수정 버전을 구분한다.

## 3. 기능 실행: 구체적으로 무엇을 하는가

하나의 실행에서 다음 흐름을 이어서 확인한다.

1. 앱을 켜서 지도와 현재 위치가 표시되는지 확인한다.
2. 위치 입력이 갱신될 때 시점이 따라오는지, 방향을 바꾸었을 때 전방 화면이 바뀌는지 확인한다.
3. 목적지를 선택하고 안내를 시작하여 경로가 표시되는지 확인한다.
4. 목적지를 다른 곳으로 변경해 새 목적지와 경로로 갱신되는지 확인한다.
5. 목적지 반경에 진입했을 때 도착 UI 또는 이벤트가 발생하는지 확인한다.
6. 관찰한 오류와 대체 표시가 있으면 정상 실행과 함께 남긴다. 이미 발생한 오류의 영상·로그도 사용할 수 있다.

특정 장소 한 곳의 성공만으로 전체 동작을 대표하지 않도록 서로 다른 출발·목적지 쌍과 반복 횟수를 구분한다. 최종 사례 수·반복 횟수는 실제 실행 계획으로 확정하며 이 안내가 학과의 지정 횟수를 의미하지 않는다.

### 남겨야 할 자료

- GPS 확인부터 경로·도착까지의 연속 화면 녹화. 화면 사진도 보조로 남긴다.
- 같은 실행의 Unity/단말/서버 로그. 영상과 로그가 어느 시도인지 연결되어야 한다.
- 실험별 출발점·목적지, 시도 횟수와 단계별 정상·오류·미수행 여부.
- 경로 출처(API·도로 메시·NavMesh)와 완전 경로·부분 경로+보조 직선·전체 직선 대체·실패 구분. 출처를 알 수 없으면 추측하지 말고 미확인으로 남긴다. 기존 로그에서 확인되지 않는 항목은 측정 전에 기록 수단을 마련해야 한다.
- GPS 미수신, API 실패·내부 탐색 실패 및 DEM 누락 등의 조건을 확인했다면 그 입력과 결과를 함께 남긴다. 오류를 관찰하지 않은 항목을 오류 대응 성공으로 채우지 않는다.

간단한 전달 양식:

```text
실험 ID / 빌드 / 날짜:
실제 단말·OS / 실행 장소 / 현장 또는 모의 입력:
출발점 / 목적지 / 목적지 변경 여부:
GPS 수신·시점 갱신:
목적지·경로 갱신:
경로 출처 / 완전·부분·직선·실패:
도착 이벤트 정상·누락·중복:
관찰한 오류:
영상·로그 파일명:
```

도착은 설정한 수평 반경의 이벤트 확인이며 실제 출입구 도달이나 경로의 보행 안전성 검증과 구분한다. Unity에서 좌표를 고정·재생한 결과도 내부 기능 점검에 사용할 수 있지만 스마트폰 현장 GPS 실험으로 기록하지 않는다.

## 4. 화면 판단: 어떤 이미지와 사람의 응답이 필요한가

동일한 장소·시점·경로를 아래 세 시각 조건으로 준비한다.

| 조건 | 표시 내용 | 확보 자료 |
|---|---|---|
| 화면 조건 1 | 건물 | 이미지 또는 짧은 영상 |
| 화면 조건 2 | 건물+지형 | 같은 장소·시점의 이미지 또는 영상 |
| 화면 조건 3 | 건물+지형+지표면 이미지 | 같은 장소·시점의 이미지 또는 영상 |

지형을 감출 때 카메라·건물·경로의 높이까지 달라지면 시각 요소 외의 차이가 섞인다. 계산용 지면 기준은 유지하고 표시만 바꾼다. 목적지 표지·경로 정보량·화면 길이도 맞춘다. 지표면 이미지에 건물 지붕이 포함될 수 있으므로 세 요소가 완전히 독립된 실험으로 해석하지 않는다.

### 판단 과제의 내용

- 실제 사진·위치 자료의 건물이 화면의 어느 건물인지 식별.
- 해당 화면에서 진행해야 할 방향 선택.
- 표시된 목적지가 어느 건물 또는 지점인지 식별.

화면과 장소 정보가 있으면 문항·선택지·기록 양식은 제가 작성할 수 있다. 정답은 현장 사진, 명확한 자료 식별 또는 사전 확인한 경로로 확정해야 한다. 정답 여부를 평가자의 느낌만으로 정하지 않는다.

### 사람별로 남길 원자료

```text
참가자 ID: P01 등 익명 ID
팀원 여부 / 해당 지역 친숙도:
화면 조건 / 문항 ID / 제시 순서:
사전 정답 / 실제 응답 / 정답·오답·무응답·시간 초과:
응답시간(초) / 시간을 측정한 방법:
화면 명확성 점수:
예상 유용성 점수:
선호 조건과 이유:
```

설문은 예를 들어 같은 1~5점 척도를 쓰되 실제 문항과 점수의 뜻을 통일한다. 응답시간은 문제·판단 화면을 제시한 때부터 답할 때까지로 기준을 맞춘다. 정답 응답시간과 오답·무응답을 분리한다. 측정하지 않은 시간을 추정해 입력하지 않는다.

사람별 원응답이 있으면 정답률·시간 요약·설문 차트는 제가 만들 수 있다. 같은 사람이 여러 문항에 답한 수를 참가자 수로 세지 않는다. 같은 장소의 정답을 세 번 학습하지 않도록 구간과 조건 순서를 조정한다. 팀원만 참여하면 실제 인원과 관계를 명시한 내부 예비평가로 보고한다.

## 5. 자료 추가·교체: 무엇을 바꾸고 비교하는가

기존 구역과 다른 소구역의 건물 자료를 적용하는 사례로 시작할 수 있다. 두 구역은 DEM 조회 및 도로자료 확보 범위 안에서 정한다. 원자료의 다른 부분을 사용하는 것도 해당 형식의 지역 적용 범위를 확인하는 사례가 된다.

여기서 구역 A/B는 지역 구분이고, 실험 빌드 A/A-1은 소프트웨어 상태의 구분이다. 기록할 때 `빌드 A(0.1.0) / 구역 B`처럼 함께 적는다.

### 남겨야 할 자료

- 두 구역의 위치·경계와 실제 사용 파일명 또는 접근 가능한 경로.
- 각 구역에 적용한 좌표계·건물 높이 입력·지형 작업 등 실제 설정.
- 파일·URL·설정·레이어·NavMesh·장면 참조·전처리·코드 중 무엇을 바꾸었는지의 간단한 메모.
- 각 구역의 건물 표시 화면과 GPS 시점·경로·도착 확인 결과.
- 변환 서버 출력 보고서: 원본 수, 최종 적용 수, 경계 절단 수, 범위 밖 제외 수, NoData 제외 수. 보고서가 로컬에 있으면 제가 추출할 수 있다.
- 실패한 경우 그 원인과 추가 작업. 코드 수정이 필요했다는 결과도 재사용 조건을 설명하는 자료가 된다.

간단한 전달 양식:

```text
구역명 / 사용 빌드 / 날짜:
범위 / 실제 입력 파일 / 지형 작업 ID:
건물 높이 입력 / 좌표계:
변경한 파일·URL·설정·장면·코드·전처리:
건물 표시 / 위치·시점 / 경로 / 도착 결과:
실패·추가 작업:
화면·로그·보고서 파일명:
```

건물만 보인 결과와 안내 기능까지 유지된 결과는 구분한다. 자동 절단·제외가 있으면 남은 자료의 적용 성공을 원자료 전체의 성공으로 확대하지 않는다. 구역 B를 모의 위치로 확인했다면 그 사실을 기록한다.

## 6. 제가 처리할 수 있는 부분

- 실제 사용 버전에 접근할 수 있을 때 Unity·Cesium·서버 설정, 커밋·파일 해시를 추출한다.
- 입력 파일과 변환 보고서가 있으면 메타데이터·객체 수·제외 수를 정리한다.
- 원응답과 로그를 바탕으로 성공률·정답률·응답시간과 설문 결과를 계산하고 표·차트를 작성한다.
- 조건·절차를 논문 문장으로 정리하고 결과 해석, 한계·결론, 그림 배치·참고문헌·목차를 수정한다.

직접 실행한 단말의 실제 결과, 참가자가 실제로 한 응답, 기록되지 않은 과거 수치·시간은 코드에서 만들어 낼 수 없다. 차트나 최종 점수만 보내기보다 계산 전 기록을 함께 보관한다.

## 7. 우선 전달하면 되는 묶음

먼저 실제 단말의 연속 실행 영상, 같은 실행 로그, 단말 기종·OS와 날짜·장소, 사용한 빌드·입력 자료를 전달한다. 이를 확인하여 기능 평가에 채울 수 있는 항목과 추가로 기록해야 할 항목을 구분한다. 다음으로 화면 조건별 자료와 사람의 응답, 자료 교체의 전후 기록을 같은 방식으로 모으면 된다.
