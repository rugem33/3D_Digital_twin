# 졸업논문 연구 초점, 확인 사항 및 보완 과제

정리일: 2026-10-04 (Asia/Seoul)

최신 종합안: 2026-10-05, 21절 참조. 연구의 두 축과 평가 제안을 한곳에 정리했다. 17~18절의 처리별 비교는 해당 개선을 주장할 경우 사용하는 세부 검증 후보이며, 연구의 두 축을 대체하지 않는다.

이 문서는 현재까지의 논문 논의, 사용자 결정, 프로젝트 파일 확인 결과와 보완 사항을 모은 작업 문서다. 실험 결과 보고서가 아니며, 미측정 수치나 개선 효과를 사실로 제시하지 않는다. 프로젝트 코드와 기존 DOCX 초안은 수정하지 않았다.

현재 연구의 중심은 **제한된 지역에서 데이터들을 연계한 스마트폰 1인칭 3D 내비게이션의 설계·구현과 데이터 추가·지역 확대를 고려한 구조**다. 높이 처리는 기능을 구성하는 구현 조건으로 두며, 절대 고도 정확도 개선이나 새로운 수직 기준 보정 방법을 핵심 기여로 주장하지 않는다. 아래의 높이 관련 상세 검토는 구현 조건과 확장 시 한계를 설명하기 위한 기록이다.

## 1. 현재 연구 방향과 확정 조건

| 항목 | 현재 정리 | 근거 및 상태 |
|---|---|---|
| 연구 유형 | 데이터 연계형 1인칭 3D 내비게이션의 시스템 설계·구현 | 새 경로 탐색 알고리즘이나 고도 보정 방법의 제안으로 설명하지 않음 |
| 핵심 연구 초점 | 제한된 지역에서 GPS 위치·공간 표현·경로 안내를 연결하는 구현과 데이터 확장 구조 | 사용자 설명에 따라 절대 고도 정확도 개선을 핵심 과제에서 제외 |

| 실제 도로의 시각적 표현 | 지도 이미지를 활용 | 사용자 설명에 따라 탐색용 도로 메시와 시각적 지도 표현을 구분 |
| 실험 빌드의 카메라 눈높이 | 지면 기준 2m | 사용자가 실험 빌드의 적용값을 확인함 |
| 2m 선택 이유 | 시야 확보와 사용자 시점의 일치 정도 사이의 절충 | 사용자 설명; 최적 높이나 편의성 향상이 검증된 결과라는 뜻은 아님 |
| 스마트폰 동작 | 사용자가 동작 확인을 보고함 | 이번 검토에서 실기 실행이나 성능 측정을 수행한 것은 아님 |
| 스마트 글래스 | 결론·향후 연구에서 개인용 기기로의 확장 가능성 논의 | 현재 특정 기기 선정·이식·검증을 연구 범위에 포함하지 않음 |
| 실측 결과 | 공란과 삽입 표시 유지 | 사용자 요청; 임의 수치 생성 금지 |
| 비교 조건·실험 절차·지표·판정 기준 | 상세 설계 보류 | 앞선 목록의 7~10번은 추후 정립 |

공공데이터포털을 사용했다는 출처 설명은 사용자가 제시했다. 논문 참고문헌과 데이터 명세에는 자료별 정확한 제목, 제공기관, URL, 취득일과 제작·갱신 시점을 추가해야 한다.

## 2. 주제와 연구 목적의 정립

### 2.1 잠정 제목

**이기종 공간데이터 기반 Cesium 1인칭 3D 내비게이션의 설계 및 구현: 데이터 연계와 지역 확장 구조를 중심으로**

민간 자료를 실제로 적용하지 않았다면, 제목·초록에서 공공·민간 데이터의 통합을 완료한 것처럼 표현하지 않는다. 민간 자료 연계는 설계상 지원 가능 범위 또는 향후 확장으로 기술한다.

### 2.2 연구 목적

건물·지형·도로·시설물 데이터와 스마트폰 GPS 위치를 연결하여, 사용자가 자신의 위치와 주변 공간 및 이동 경로를 1인칭 시점에서 확인하는 3D 내비게이션 시스템을 설계·구현한다. 유성구의 제한된 지역 사례에서 기능과 데이터 처리 흐름을 설명하고, 지원 형식 내 자료 추가·교체 및 지역 확대에 필요한 조건과 제약을 정리한다. 지형 기준 카메라 높이와 경로 표면 처리는 이 기능을 구성하는 구현 방법으로 다룬다. 실제 해발고도 일치나 GPS 고도의 절대 정확도 개선은 현재 연구 목적에 포함하지 않는다.

### 2.3 핵심 연구 문제 후보

1. 이기종 공간자료와 GPS 위치를 연결한 스마트폰 1인칭 3D 내비게이션을 어떤 데이터 처리 흐름과 시스템 구조로 구성할 수 있는가?
2. 제한된 대상 지역에서 현재 위치·카메라 시점·목적지·경로 표시가 연결되는 기능을 구현하고 확인할 수 있는가?
3. 지원 데이터 형식 내에서 자료를 추가·교체할 수 있는 구현 범위는 어디까지이며, 지역 확대와 개인용 기기 활용에 남는 제약은 무엇인가?

기능 동작은 사용자 관찰과 구현 기록, 정량적 성능이나 효과는 실제 측정 결과로 구분한다. 기능별 확인 절차와 실험 지표의 상세 설계는 기존 합의대로 보류한다. 앞서 검토한 높이 정확도 개선 주장은 현재 핵심 연구 문제에서 제외한다.

## 3. 높이 처리의 구현 목적과 주장 범위

### 3.1 사용자 제안과 판정

사용자 설명: GPS 높이를 직접 사용하면 DEM으로 표현한 지형과 높이가 맞지 않는 현상이 있으며, 좌표·높이 기준과 DEM 해상도 등에 따른 불일치의 영향을 줄이기 위해 지형 기반 높이 처리를 사용했다.

이를 **GPS 고도와 표현된 지면 사이의 불일치를 줄이려는 구현 목적**으로 기록한다. DEM의 좌표계나 해상도가 GPS 수신 고도 자체의 측정 오차를 만들어 낸다고 설명하지 않는다. 관찰된 불일치의 원인이 좌표 변환, 수직 기준 차이, DEM 해상도, GPS 측정 변동 중 무엇인지는 아직 분리해 검증하지 않았다.

아래 구분은 높이 처리를 설명하기 위한 것이다. 현재 논문의 중심을 고도 정확도 개선 연구로 바꾸기 위한 요구사항은 아니다. 수평 좌표 변환, 수직 기준 변환, GPS 고도의 변동 억제, 지형에 대한 화면 정합은 서로 다른 문제다.

- 좌표 변환은 동일한 실제 위치를 다른 좌표 표현으로 연결한다. 이 과정만으로 원본 데이터나 GPS 측정의 정확도가 높아지지는 않는다.
- 카메라 높이를 GPS 고도 대신 DEM에서 얻은 높이로 설정하면 GPS 고도 변동의 화면 반영을 줄일 수 있다. 이는 GPS 센서 측정값을 정확하게 보정한 것과 구분한다.
- DEM과 GPS의 높이 기준이 다르면 기준 변환이 필요하다. 현재 코드에서 명시적인 지오이드 기반 수직 기준 변환은 확인하지 못했다.
- 단일 90m DEM으로 검토하는 경우, 여러 DEM의 고도 차이를 일반적으로 해결했다고 주장할 수 없다.
- 같은 DEM으로 높이를 설정하고 같은 DEM과의 차이만 계산하면 내부 표현 일관성을 평가할 수 있으나, 현실에 대한 절대 높이 정확도는 입증하지 못한다.

### 3.2 현재 구현 설명과 핵심 기여의 구분

**“1인칭 내비게이션의 카메라 시점을 가상 지면과 연결하기 위해 공급된 지형 표면 높이를 참조하고, 별도 도로 데이터와 경로 표시를 연계하였다.”**

이는 구현 방법의 설명이다. 고도 정확도가 개선됐다는 결과 주장으로 바꾸지 않는다. 핵심 기여는 자료 변환, GPS 기반 시점, 목적지·경로 표시를 하나의 시스템으로 연결한 설계와 적용 범위를 명시하는 데 둔다. 새로운 고도 보정 방법이나 여러 자료의 자동 수직 정합을 제안한 것으로 설명하지 않는다.

추가로, GPS 고도는 수신기가 놓인 높이를 포함할 수 있고 DEM은 지면을 나타낸다. 두 값의 차이를 모두 오차로 취급하지 않는다. 카메라 눈높이 2m도 의도한 표현 오프셋이므로 지면 정합 오차와 분리한다.

## 4. 좌표계 통일은 어디까지 필요한가?

### 4.1 결론

**원본 파일을 모두 하나의 EPSG 코드로 바꾸어 저장할 필요는 없다. 함께 표현·비교할 때는 일관된 공간 참조와 변환 과정이 필요하다.**

원본의 좌표계와 제작 기준을 보존하고, 각 데이터의 처리 경로에서 공통 표현 공간으로 변환하는 방식이 적절하다. 거리 오차를 계산할 때에는 도 단위 경위도 차이를 그대로 미터 오차로 취급하지 않고, 미터 단위 비교 공간이나 지리적 거리 계산을 사용해야 한다. 구체적인 지표 설계는 추후 정립한다.

여기서 ‘일관된 기준’은 동일한 실제 장소를 표시하는 자료들이 다음 네 조건을 공유하거나, 차이를 명시적으로 변환한다는 뜻이다.

| 조건 | 의미 | 이 프로젝트에서의 적용 |
|---|---|---|
| 위치를 해석하는 좌표계 | 같은 숫자가 어떤 실제 위치를 뜻하는지 일치 | EPSG:5186 건물, EPSG:5179 DEM, GPS 경위도를 각 원본 CRS에 맞게 변환 |
| 기준점과 축 방향 | 같은 위치를 Unity에서 같은 기준점·축으로 표현 | 같은 CesiumGeoreference를 통해 ECEF에서 Unity 좌표로 연결; 기준점 변경 시점도 고려 |
| 단위 | 좌표 차이나 높이를 동일한 단위로 해석 | 경위도의 도와 투영 좌표·거리의 미터를 구분 |
| 높이의 기준면 | 높이 0의 의미가 일치 | 정표고·타원체고를 구분하고 필요한 변환을 명시; 지면 기준 눈높이 2m는 별도 오프셋 |

즉, ‘좌표 숫자를 같게 만든다’는 의미가 아니라 **같은 실제 위치가 같은 표현 위치로 연결되게 한다**는 의미다. 지금 ECEF와 Cesium을 통한 연결 구조는 있지만 수직 기준이 일치한다는 확인까지 완료된 것은 아니다. [CesiumGeoreference 공식 문서](https://cesium.com/learn/cesium-unity/ref-doc/classCesiumForUnity_1_1CesiumGeoreference.html)

### 4.2 확인된 좌표계와 변환 경로

| 자료·단계 | 확인 결과 | 주의점 |
|---|---|---|
| 건물 SHP 원본 | EPSG:5186, Korea 2000 / Central Belt 2010 | ZIP 내 `.prj`의 AUTHORITY 항목과 장면 변환 설정 확인 |
| 로컬 원본 DEM | EPSG:5179, KGD2002 / Unified CS | GeoTIFF GeoKey에서 확인 |
| 도로 원본 자료 | DEM과 다른 자료이며 원본에 높이값 없음 | 고정 1m는 메시 생성 설정값; 실제 도로 표고나 독립 높이 정답으로 사용하지 않음 |
| 서버 DEM 재투영 목표 | EPSG:4326 | `gdalwarp -t_srs EPSG:4326 -r bilinear`; 원본 NoData 감지 후 옵션 적용 |
| GPS 입력 | 위도·경도·고도 입력을 WGS84 타원체 계산에 전달 | 모바일 고도의 실제 수직 기준이 이 계산과 일치하는지는 별도 확인 필요 |
| 공통 지리 표현 | ECEF 및 Cesium 지리 기준점에 따른 Unity 좌표 | 수평·수직 기준을 함께 관리해야 함 |

건물 데이터는 타일러에서 좌표 변환을 수행한다. DEM과 동일한 EPSG:4326 중간 파일을 반드시 거쳐야 하는 것은 아니다. 마지막에 공간 참조가 일관되게 연결되는지가 핵심이다.

### 4.3 수직 기준은 별도로 정립해야 함

**DEM 수직 기준은 ‘DEM의 높이 숫자를 어디를 0으로 놓고 측정했는가’라는 뜻이다. 줌 레벨이나 타일 분할 설정과 다른 항목이다.**

- 해발고도에 해당하는 정표고: 평균 해수면에 가까운 기준면인 지오이드를 기준으로 한 높이.
- 타원체고: 지구 형상을 계산하기 위해 사용하는 기준 타원체 표면에서부터의 높이.
- 같은 장소라도 두 기준으로 표현한 높이 숫자는 다를 수 있다. 따라서 같은 ‘m’ 단위만으로 높이 기준이 일치한다고 판단하지 않는다.
- 이를 확인하는 자료는 DEM 공급기관의 설명이나 원본 메타데이터다. 현재 확인한 수평 EPSG 코드와 z=7만으로 어느 수직 기준인지 결정할 수 없다.

정표고 H, 타원체고 h, 지오이드고 N은 일반적으로 `h = H + N`의 관계로 구분한다. 카메라 눈높이 2m는 이 수직 기준 변환에 사용되는 값이 아니다.

EPSG:4326으로 수평 재투영했다는 사실만으로 DEM의 픽셀 높이가 타원체고로 변환됐다고 볼 수 없다. GDAL의 수직 변환에는 명시적 수직/3차원 CRS 또는 적절한 변환 과정과 관련 격자 자료 등의 조건이 필요하다. [GDAL 공식 문서](https://gdal.org/en/stable/programs/gdalwarp.html#vertical-transformation)

현재 필요한 확인 사항은 DEM의 높이 기준·단위, GPS 고도의 플랫폼별 의미, Cesium에 공급하는 지형 높이의 기준이다. 사용자의 z=7 최적화 목적 설명은 아래 타일 운영 조건에 반영하며, DEM 수직 기준은 **미확인**으로 유지한다. 확인 전에는 절대 높이 오차 개선을 단정하지 않는다.

이 항목은 데이터 명세와 확장 시 한계로 남긴다. 현재 연구에서 절대 고도 정확도 개선을 주장하지 않으므로, 원본 수직 기준 확인과 통일을 제한 지역의 기능 검토를 진행하기 위한 필수 선행 작업으로 두지 않는다. 지역이 작다는 사실만으로 높이 기준의 차이가 없어지는 것은 아니며, 현재 기능 범위에서 영향이 크지 않았다는 관찰과 적용 범위를 함께 기록한다.

### 4.4 현재 확인 범위: 공급된 타일 높이와 상대 배치

사용자는 타일 적용 과정에서 제공된 높이를 그대로 사용했고, 좌표계가 다른 자료와 도로 메시도 대체로 비슷한 높이에 배치되는 것을 관찰했다고 설명했다. 이 내용은 **사용자에 의한 구현 관찰**로 기록한다. 위치별 정량 오차 측정이나 실제 해발고도와의 비교가 완료됐다는 의미로 사용하지 않는다.

현재 구분은 다음과 같다.

| 항목 | 확인 수준 |
|---|---|
| 공급된 지형 타일의 표면 높이를 카메라 시점에 활용 | 구현 코드와 사용자 설명으로 확인 |
| 자료와 도로 메시가 화면에서 대체로 비슷한 높이에 위치 | 사용자 관찰; 정량 오차는 미측정 |
| 원본 DEM의 값이 해발고도인지 타원체고인지 | 미확인 |
| 변환 과정에서 원본의 수직 기준이 올바르게 처리됐는지 | 미확인 |
| 실제 지형에 대한 절대 높이 정확도 | 미검증 |

Cesium의 `SampleHeightMostDetailed`는 출력 높이를 타원체(통상 WGS84) 기준 미터로 정의한다. 하지만 API의 출력 정의는 원본 DEM의 수직 기준이 확인되고 올바르게 변환됐다는 증거가 아니다. [Cesium 공식 높이 조회 문서](https://cesium.com/learn/cesium-unity/ref-doc/classCesiumForUnity_1_1Cesium3DTileset.html)

현재 논문에서는 **공급된 타일 표면에 대한 카메라·경로의 상대적 배치**를 기능 구현 조건으로 기록한다. 높이 정합 자체를 핵심 개선 실험으로 두지 않는다. 서로 비슷하게 배치된 관찰은 해당 지역의 기능 구현을 설명하는 근거가 될 수 있으나, 현실의 해발고도 일치나 GPS 고도의 절대 오차 개선을 입증하지 못한다. 자료들이 같은 높이 편차를 공유하는 경우에도 서로는 맞아 보일 수 있기 때문이다.

Virtual globe의 지표면은 사용한 지형 자료가 표현하는 표면이다. 화면에서 지표면에 붙어 있다는 사실만으로 실제 해발고도 기준임을 확정하지 않는다. 논문에는 원본 수직 기준의 미확인을 한계로 남기고, 확인 전까지 해발고도가 반영됐다고 단정하지 않는다.

## 5. 90m DEM과 2m 시점 설정

### 5.1 DEM 확인 결과

- 장면에 저장된 DEM 파일 경로: `C:/mago-3d-tiler/output_file.tif`.
- 확인한 로컬 파일의 크기: 256 × 315 픽셀.
- 원본 픽셀 간격: 90m × 90m.
- 원본 수평 좌표계: EPSG:5179.
- NoData: -9999.
- 프로젝트 루트의 `output_file.tif`에서도 같은 메타데이터가 확인됐다.
- 이미 재투영된 `Tools/_work/wgs84.tif`는 EPSG:4326, 경위도 단위 격자다. 재투영 뒤 경위도 격자를 원본 90m와 동일한 단위의 숫자로 비교하지 않는다.
- 장면이 사용하는 원격 지형 작업의 업로드 원본이 현재 로컬 파일과 동일한지는 별도 확인 대상이다.

90m는 수평 격자 간격이며 수직 정확도나 GPS 오차 범위를 뜻하지 않는다. 타일 생성과 재표본화로 새로운 고정밀 원본 정보를 얻은 것으로 해석하지 않는다.

도로는 별도 자료로 구현됐으므로 도로 모델의 수평 상세도를 DEM 격자 간격과 동일하다고 설명하지 않는다. 원본 도로 자료에 실제 높이값은 없고 메시 생성에는 고정값 1m를 사용했다. 따라서 도로 메시 자체를 실제 도로 표고나 고정밀 3D 도로 측량 자료로 해석하지 않는다. 카메라 높이와 일부 경로 표면 처리에 DEM 지형이 사용되므로 DEM의 높이 한계는 해당 처리 단계에 남는다. DEM만을 이용하는 처리에 대해서는 도로 단차, 좁은 경사로, 교량, 출입구 등 세부 지형의 정합성을 보장하지 않는다.

### 5.2 눈높이 2m의 논문 기록

권장 설명: “카메라 시점은 지면 기준 2m로 설정하였다. 높은 시점은 주변 공간의 시야 확보에 유리할 수 있으나 실제 사용자 시점과의 차이가 커질 수 있으므로, 시야 확보와 사용자 시점의 일치 정도를 함께 고려하여 2m를 선택하였다.”

이는 설계상 선택 이유다. 사용자별 실제 눈높이를 일치시켰거나 2m가 최적이라는 실험 결과를 뜻하지 않는다.

현재 파일과 사용자 제시 조건을 구분한다.

| 항목 | 값 | 상태 |
|---|---|---|
| 사용자 확인 실험 빌드 눈높이 | 2m | 적용값 확인 완료; 논문 실험 조건으로 기록 |
| `FirstPersonGPSController.cs` 기본값 | 2m | 코드 확인 |
| 현재 `Assets/level2.unity`의 저장값 | 3m | 현재 작업 파일의 확인값; 사용자가 확인한 실험 빌드 2m와 구분 |
| 경로 렌더러 `_groundOffset` | 2m | 카메라 눈높이와 다른 변수 |
| 경로 렌더러 `_terrainSnapOffset` | 0.05m | 지표면 경로 표시 오프셋; 적용 처리 단계가 다름 |

사용자는 실험 빌드가 2m 설정으로 동작했다고 확인했다. 논문에는 실험 조건을 2m로 기록한다. 현재 작업 장면의 3m 저장값은 별도의 프로젝트 스냅샷 정보로 남기며, 이 차이를 실험 빌드 설정의 미확인 항목으로 반복하지 않는다. 이번 문서 작업에서는 프로젝트 장면을 변경하지 않았다.

## 6. GPS와 지형 높이 처리의 실제 구현

1. `GPSLocationService`가 위도·경도·고도를 받아 ECEF에서 Unity 좌표로 변환하고 보간 좌표를 제공한다.
2. `FirstPersonGPSController`는 GPS 수평 위치를 바탕으로 카메라 목표 위치를 갱신한다. 점프 거부와 건물 겹침 보정도 영향을 줄 수 있으므로 최종 카메라 위치를 원시 GPS와 동일한 값으로 취급하지 않는다.
3. 지형 높이는 연결된 `Cesium3DTileset.SampleHeightMostDetailed`로 조회하고, 성공 시 캐시된 지면 높이에 눈높이를 더한다.
4. 최초 또는 수평 이동이 일정 거리(코드상 2m)를 넘는 조건에서 높이를 다시 확인한다. 이 2m 이동 조건도 눈높이 2m와 별개다.
5. 지형 샘플링 실패 시 Raycast로 지면을 찾는다. 지면 캐시가 아직 없으면 GPS 고도에서 변환된 위치에 눈높이를 더하는 경로가 있다.
6. 경로 안내선은 별도의 표면 Raycast와 렌더링 오프셋으로 높이를 처리한다. 카메라와 완전히 같은 높이 취득 방법이라고 설명하지 않는다.
7. `PositionProvider.PlayerPosition`은 GPS 보간 좌표이고, 경로 계산의 `NavPosition`은 카메라 지면 앵커 등을 우선한다. 모든 기능이 같은 최종 보정 좌표를 사용한다고 쓰지 않는다.

### 도로·지형 자료와 실제 경로 높이의 구분

사용자는 다음의 도로 구현 방식을 확인했다.

- 원본 도로 자료에는 높이값이 없다.
- 메시 생성에 고정값 1m를 적용했다. 이 값은 원본에서 측정한 도로 고도가 아니다. 두께·돌출 높이·오프셋 중 구체적으로 어떤 생성 매개변수인지의 세부 명칭은 현재 자료만으로 확정하지 않는다.
- 도로 메시는 내비게이션 경로 탐색에 활용한다.
- 실제 도로의 시각적 표현은 지도 이미지로 제공한다. 지도 이미지와 탐색용 메시의 역할을 구분한다.

논문 기재 방향: “원본 도로 자료에 높이 속성이 없어 메시 구성에 고정 높이값 1m를 적용하였으며, 이를 경로 탐색용 공간으로 사용하였다. 도로의 시각적 표현에는 지도 이미지를 활용하였다. 메시의 설정값을 실제 도로 표고로 해석하지 않는다.”

장면에서도 Road와 Land 레이어가 구분되어 있고, 경로 렌더러의 마스크는 각각 64와 128이다.

다만 현재 `RouteRenderer.ProjectToRoadSurface`의 실제 호출 순서는 **Land 마스크의 지형 샘플링 → 실패 시 Road 마스크 샘플링 → 카메라 기준 대체 위치**다. 코드 주석에 적힌 ‘도로 우선’ 순서와 다르므로 논문은 실제 코드 기준으로 작성한다. 경로 정점의 별도 지형 스냅 단계도 있다. 따라서 도로 자료가 별도라는 사실과 경로 표시 높이가 언제나 도로 모델을 따른다는 주장은 구분한다.

이는 이번 확인에서 기록한 구현 조건이다. 코드 변경이나 도로 우선으로의 수정은 수행하지 않았다.

참고: Cesium 좌표 변환은 타원체 기준 높이를 다룬다. [Cesium 공식 좌표 API](https://cesium.com/learn/cesium-unity/ref-doc/classCesiumForUnity_1_1CesiumEllipsoid.html)

## 7. 평탄 타일 우회 처리와 논문 기재

### 7.1 ‘7m 추가’에 대한 확인

현재 코드의 `FLAT_ZOOM_LEVELS = {7}`에서 **7은 높이 7m가 아니라 줌 레벨 z=7**이다. 확인한 관련 코드에서는 지형 높이에 일괄 7m를 더하는 보정을 찾지 못했다. 과거 다른 구현에서 7m를 사용했는지는 현재 확인 결과만으로 배제할 수 없다.

z는 지형 타일을 공간적으로 분할하는 계층 단계다. 일반적으로 단계가 높아질수록 더 작은 영역의 상세 타일을 사용한다. 화면을 확대하거나 카메라가 지형에 가까워질 때 높은 단계가 선택되는 것과 관련이 있지만, 화면의 ‘7배 확대’, 특정 UI 줌 값 또는 카메라 높이 7m를 뜻하지 않는다. Cesium은 시점과 화면상 오차 등 조건에 따라 사용할 타일을 선택한다. [quantized-mesh 공식 규격](https://github.com/CesiumGS/quantized-mesh)

따라서 논문에서는 ‘화면 확대 7단계에서 높이를 보정했다’보다 **‘지형 타일 계층의 z=7에서 우회 처리를 적용했다’**고 적는다.

사용자는 이 계층 처리를 최적화 목적으로 사용했다고 설명했다. 논문에는 **타일 로딩·상세도 운영을 위한 구현 조건**으로 정리한다. 현재 코드에서 확인되는 것은 z=7 등에 대한 특수 평탄 대체이며, 모든 지형을 z=7 하나만으로 제공하는 설정이나 최적화 효과의 실측 결과를 뜻하지 않는다.

### 7.2 현재 구현의 동작

- z≤4와 z=7에서 최소 평탄 타일로 교체한다.
- 생성 타일의 네 정점 높이 값은 모두 0이고, 타일 헤더의 minimumHeight는 0이다. 따라서 표면은 높이 0m다.
- 헤더의 maximumHeight에는 DEM 최대 고도를 넣는다. 이 값은 모든 정점을 DEM 최대 높이로 올리는 설정이 아니다.
- 코드 주석은 ECEF 중심 및 낮은 상세도 타일에서의 상세 타일 탐색 문제를 우회하기 위한 처리라고 설명한다. 원인에 대한 외부 재현 검증을 수행한 것은 아니다.
- z=5, z=6, z≥8은 이 교체 조건에 포함되지 않는다. 이것만으로 해당 타일 전체가 정상임을 보장하지는 않는다.
- 현재 통합 서버에서 누락 타일은 `None`으로 처리되어 HTTP 404를 반환한다. 파일 상단 주석과 오래된 도구의 ‘누락 시 평탄 대체’ 설명과는 구분한다.

### 7.3 기재해야 하는 이유와 위치

**기재해야 한다.** 단순한 개발 에피소드가 아니라 실제 표면 높이와 로딩 과정에 영향을 주는 구현 조건이기 때문이다.

- 구현 장: 적용 줌 단계, 목적, 대체 방식과 헤더 설정을 설명한다.
- 실험 조건 장: 사용 지형 버전, 생성 줌 범위, 평탄 대체 조건을 기록한다.
- 논의·한계: 상세 지형 로딩 전 또는 샘플링 조건에 따라 원본 지형과 다른 표현이 나타날 수 있음을 기술한다. 실제 영향이 없었다고 쓰려면 확인 근거가 필요하다.

권장 기록: “일부 줌 단계에서 상세 지형 로딩을 방해하는 현상을 우회하기 위해 최소 지형 타일을 적용하였다. 대체 단계는 z≤4 및 z=7이며, 대체 표면의 높이는 0m이다. 이 처리가 높이 표현에 미치는 영향은 평가 조건과 함께 구분한다.”

## 8. 데이터 확장성의 주장 범위와 논문으로서의 의미

아래의 제한된 확장성 범위로 진행하기로 사용자와 정리했다. 전국 운영 가능성이나 임의 자료의 자동 호환을 연구 성과로 확대하지 않는다.

### 8.1 현재 주장 가능한 범위

- 지원 형식과 좌표·높이 메타데이터가 주어진 자료를 기존 변환·표현 경로에 추가하거나 교체할 수 있는 구조를 구현했다.
- 건물 데이터는 SHP 등 지원 입력에서 3D Tiles로, DEM은 지형 타일로 제공하는 처리 구조를 설명할 수 있다.
- 지형 공급원은 Cesium Ion, 사용자 URL 등으로 전환하는 기능이 있다.
- 시설물은 좌표 자료에 따라 배치할 수 있지만 현재 장면 객체로 관리한다. 지형·건물 타일과 같은 전국 단위 자동 스트리밍 구조로 취급하지 않는다.
- 지역 확대를 고려할 수 있는 기반 구조를 설명하되, 실제 확인 지역은 유성구로 한정한다.

### 8.2 현재 주장하지 말아야 할 범위

- 전국 어디서나 같은 품질과 성능으로 운영할 수 있음.
- 모든 공공·민간 3D 형식의 자동 호환과 정합을 보장함.
- 민간 고정밀 자료, 접근 제어, 여러 사업자의 동적 자료 발견·통합을 이미 검증함.
- 여러 DEM의 높이 기준 차이를 자동으로 해결함.

### 8.3 논문으로서 의미가 있는 범위

졸업논문에서는 유성구의 제한된 자료를 대상으로 처리 구조, 문제 해결 과정, 지원 범위와 한계를 재현 가능하게 정리하는 설계·구현 연구가 될 수 있다. 전국을 구현해야만 의미가 생기는 것은 아니다.

저널 수준에서는 ‘Cesium을 사용했다’ 또는 ‘데이터를 추가할 수 있다’만으로 신규성이 충분하지 않다. 데이터 연계·교체에 필요한 조건, 지역 의존적인 구성과 재사용 가능한 구성의 경계, 모바일에서의 적용 제약 등 기존 연구와 구분되는 일반화 가능한 결과가 필요하다. 구체적인 효과와 신규성은 추후 비교 자료와 실측으로 판단한다. 높이 기준 문제는 확장 시 제약 중 하나로 다루며 논문 전체의 중심으로 확대하지 않는다.

정리할 기여는 **국내 최초 앱**보다 **제약이 있는 공간자료에서 1인칭 위치·경로 표현을 연결하는 구현 방법과 적용 한계를 명시한 사례**다.

## 9. 스마트폰 검증과 스마트 글래스 활용성

### 9.1 사용자 제안 방향의 채택

스마트폰에서 1인칭 3D 내비게이션의 동작을 확인하고, 스마트 글래스 등 개인용 기기로의 확장 가능성을 결론·향후 연구에서 논의하는 방향을 채택한다. 현재 단계에서 특정 글래스 기종을 반드시 선정할 필요는 없다.

### 9.2 스마트폰 동작으로 설명할 수 있는 범위

- 해당 스마트폰 환경에서 위치·공간 표현·경로 표시 기능의 동작을 확인했다는 사실.
- 데이터 변환과 경로 정보의 일부를 다른 표현 장치에서도 재사용할 수 있다는 설계상 가능성.

스마트폰 동작 확인만으로는 정합 오차 개선, 모바일 성능 목표 달성, 전국 운영이나 XR 기기 실행을 입증하지 않는다. 해당 효과는 각각의 근거가 필요하다.

### 9.3 향후 연구에 남길 항목

- 머리·기기의 자세 입력과 지리 기준점 연결.
- 현실 중첩형 AR을 선택할 경우 공간 앵커와 실제 환경 정합.
- 기기별 렌더링 환경, 표시 범위, 입력 방법 및 자원 제약.
- 구현과 실기 검증 전에는 ‘활용 가능성’으로 표현하고 ‘호환성·이식성 검증 완료’로 표현하지 않음.

Google은 Android XR에서 GPS와 VPS를 연계한 공간 안내 데모를 공개했다. 이를 활용 배경으로 인용할 수 있지만 본 프로젝트의 이식 가능성을 직접 입증하는 자료로 사용할 수는 없다. [Google 공식 개발 사례](https://android-developers.googleblog.com/2026/06/android-xr-geospatial-api-gemini.html)

## 12. 다음 정리를 위해 필요한 자료

### 지금 필요한 자료

1. 건물·DEM·도로·시설물의 정확한 자료명, 제공기관, 공공데이터포털 URL, 취득일 및 제작·갱신 시점. 도로는 원본 파일 경로와 수평 좌표계가 필요하다. 도로 높이 속성이 없고 메시 생성값 1m를 사용했다는 설명은 사용자 확인 사항으로 기록한다.
2. 확보할 수 있다면 DEM 수직 기준과 단위가 기재된 메타데이터 또는 공급기관 설명. 현재는 미확인 한계로 기록하며, 제한 지역의 기능 중심 연구를 진행하는 필수 선행 조건으로 요구하지 않는다. 90m로 고정하므로 5m 자료 확보는 요구하지 않는다.
3. 원격 서버의 최종 지형 작업이 사용한 원본 파일과 로컬 `output_file.tif`의 대응 관계.
4. 실제로 동작을 확인한 스마트폰과 빌드 식별 정보. 실험 빌드의 눈높이 2m는 사용자 확인 완료로 기록하며 다시 미확인 설정값으로 취급하지 않는다. 상세 성능 실험 설계는 아직 진행하지 않는다.
5. 민간 자료 적용 이력이 있다면 자료 형식과 적용 범위. 없다면 민간 자료는 확장 가능성으로 명시한다.
6. 유성구 전체인지 특정 구간인지 구분할 표현·확인 범위.

### 후속 단계로 보류한 사항

비교 조건, 실험 환경·절차, 지표의 수식·분석 방법, 가설의 판정 기준을 구체적으로 설계하는 일은 사용자가 요청한 후 진행한다. 다만 ‘절대 정확도 개선’을 유지하려면 독립적인 기준 자료가 필요하다는 원칙은 남긴다.

| 기존 방식에서 확인할 사항 | 본 설계에서 제안하는 처리 원칙 | 필요한 근거 |
|---|---|---|
| 자료 출처·형식이 달라질 때 필요한 변환과 변경 작업이 어떻게 정의되는가 | 자료별 변환·설정과 안내 핵심 로직의 재사용 경계를 구분한다 | 문헌의 실제 설명, 자체 자료 교체 전후 기록 |
| 경로 계산 실패·부분 연결·직선 대체를 어떤 상태로 다루는가 | 완전 경로, 부분 경로, 대체 표시를 별도로 판정한다 | 문헌의 상태 처리, 자체 경로 출처·상태 기록 |
| 제한 지역 적용 결과를 어떤 조건까지 일반화하는가 | 확인한 형식·지역·전처리 조건 안에서만 재사용을 주장한다 | 적용 조건표, 성공·실패 사례 |

이는 문헌을 확인할 비교 축이다. 기존 시스템이 위 조건을 모두 지원하지 않는다고 단정하지 않는다. 문헌에서 설명을 찾지 못한 사항도 곧바로 기능 부재로 간주하지 않는다. 기존 연구와 같은 원칙이라면 본 연구의 기여는 제한 지역의 적용 사례와 재현 가능한 검토 결과로 조정해야 한다. 처리 원칙을 나열하는 것만으로 저널 수준의 신규성이 확보되지는 않는다.

### 16.2 기능별 성공·실패 판정 제안

| 항목 | 성공 기준 제안 | 실패 또는 별도 판정 | 기록할 자료 |
|---|---|---|---|
| GPS 연동 | 단말이 유효한 위치를 취득하고, 수용된 위치 입력의 변화가 위치·시점 갱신으로 이어진다 | 서비스 미시작, 오래된 위치 사용, 좌표 변환 실패, 위치 갱신 정지. 이상치 제거는 정상 위치 갱신과 구분 | GPS 상태·시각·위경도·제공 정확도, 수용/제외 여부, 변환 위치, 카메라 위치 |
| 경로 갱신 | 목적지 변경 또는 설정한 갱신 주기에 따른 요청이 발생하고, 의도한 요청의 결과가 현재 목적지에 적용된다 | 이전 목적지 결과 적용, 같은 목적지의 오래된 요청 결과가 새 결과를 덮어씀, 요청 또는 적용 누락 | 목적지 ID, 요청별 번호, 요청·응답·적용 시각, 요청 시작 위치, 경로 출처·상태 |
| 목적지 연결 | 선택한 목적지 좌표와 경로 종점의 수평 거리가 사전 지정 허용값 ε 이내이며, 접속 구간의 확보 수준을 확인한다 | 종점 이격, 다른 목적지 연결, 도로 밖 지점으로의 연결. 직선 접속은 별도 표시 | 목적지 좌표, 종점 좌표, 수평 거리, 시작·끝의 직선 접속 구간 |
| 도착 판정 | 실제 빌드에 설정된 수평 반경 R에 대해 d<R에서 도착 이벤트가 안내 1회당 한 번 발생하고 안내 상태가 종료된다 | d≥R에서 잘못된 도착, d<R에서 누락, 중복 이벤트, 위치 미확보 상태에서의 도착 | 사용 위치, 수평 거리 d, 설정 R, 이벤트 횟수, 안내 상태 |

GPS 연동 확인은 센서의 실제 위치 정확도 향상을 입증하지 않는다. 제공 정확도 값도 실측 위치 오차와 동일하게 취급하지 않는다. 실제 단말의 GPS 동작 확인과, 기록된 입력을 재생하는 경계·실패 조건 확인은 별도로 제시한다.

목적지 종점 확인은 먼저 선택한 좌표에 대한 기능적 연결을 평가한다. 그 좌표가 시설의 실제 입구인지, 접속 구간이 보행 가능한지는 별도 확인 대상이며 좌표 일치만으로 주장하지 않는다. NavMesh의 완전 경로도 해당 메시 안의 연결성이지 실제 보행 안전성을 보증하지 않는다.

현재 구현에서 반영해야 할 사항:

- `PositionProvider.IsReady`는 GPS 서비스 컴포넌트의 존재를 확인한다. 유효한 GPS 취득을 확인하는 기준으로 단독 사용하지 않는다.
- 거리 판정의 `PlayerPosition`과 경로 시작점의 `NavPosition`은 서로 다를 수 있다. 각각 GPS 기반 위치와 카메라/앵커 기반 위치를 기록한다.
- `NavigationService` 소스 기본값은 도착 반경 15m, 갱신 주기 10초다. 실험 빌드의 Inspector 설정을 확인하기 전에는 실험값으로 확정하지 않는다. 도착 반경 R과 경로 종점 허용값 ε도 서로 다른 판정 변수다.
- 목적지 변경·취소 시 요청 식별값은 바뀌지만, 동일 목적지의 주기 갱신마다 식별값이 증가하는 구조는 아니다. 요청이 겹칠 경우 응답 순서 역전 가능성을 확인할 필요가 있다. 현재 부하나 단말에서 실제로 발생했다고 단정하지 않는다.
- 경로 계산 이벤트는 직선 대체 결과에도 발생한다. 이벤트 발생 자체를 유효 경로 확보의 성공으로 세지 않는다.
- NavMesh 부분 경로는 목적지까지 직선 구간을 덧붙인다. 완전 경로와 구분한다. API 경로의 시작점 접속도 직선일 수 있으므로 출처뿐 아니라 접속 상태를 남긴다.

### 16.3 경로 결과와 비교 검증을 분리하기

경로 출처는 `API / 도로 메시 / NavMesh / 전체 직선 대체`로 기록하고, 연결 상태는 `완전 / 부분+직선 접속 / 대체 표시 / 결과 없음`으로 별도 기록한다. 출처와 상태를 하나의 성공 여부로 합치지 않는다. 접속 구간이 있으면 그 사실도 기록한다.

최소 확인 조건은 정상 입력, API 실패, 도로 연결 단절 또는 NavMesh 외부 목적지, 목적지 변경 중 응답 도착이다. 조건별 시도 수 n=[기록 예정], 경로 확보 수=[기록 예정], 부분 연결 수=[기록 예정], 직선 대체 수=[기록 예정], 실패 수=[기록 예정]를 별도 집계한다. 반복 횟수와 지연 허용값=[확정 예정]은 측정 전에 정한다.

개선 비교는 실제로 주장하는 항목에 한정한다.

- **대체 절차의 효과를 주장하는 경우:** 같은 시작점·목적지·자료·실패 조건에서 API 단독과 단계별 대체를 포함한 구성을 비교한다. 완전 경로 확보율, 부분 경로 비율, 표시 유지율을 따로 제시한다. 직선 표시 증가를 경로 확보 개선으로 해석하지 않는다.
- **자료 적용 작업 감소를 주장하는 경우:** 비교 가능한 기존 적용 절차를 정의한 뒤 변경한 코드·설정·장면·전처리 단계와 실제 작업량을 비교한다. 비교가 없으면 작업량의 관찰 결과와 재사용 범위만 보고한다.
- 사용성·2D 대비 우월성·절대 높이 정확도·전국 운영성을 현재의 성과로 추가하지 않는다.

### 16.4 자료 교체 기록으로 확장 주장의 경계 정하기

유성구 안에서라도 기존 자료 A와 **내용이 다른 독립 자료 B**를 추가하거나 교체하는 사례를 제안한다. 같은 자료를 다른 URL로 다시 연결하는 작업은 내용·속성 변화에 대한 재사용 검증이 아니다. 자료 한 종류의 교체 결과만으로 전체 지역 시스템의 교체 가능성을 주장하지 않는다.

| 구분 | 교체 전후 기록할 내용 |
|---|---|
| 입력 자료 | 자료명·출처·버전/식별값·범위·형식·속성·좌표계·해상도, 기존 자료와 다른 점 |
| 핵심 코드 | GPS 연동, 목적지 관리, 안내 상태 처리 코드의 변경 유무와 실제 차이 |
| 설정 | 타일 URL·자료 ID·좌표 원점·필드 매핑·높이 설정·레이어·재질 등 실제 변경값 |
| 장면 | 도로/시설물 교체·배치, 참조 재연결, 충돌체·NavMesh 준비 등 실제 작업 |
| 전처리 | 좌표 변환·필수 속성 정리·타일 생성·메시 생성·그래프 준비 등 실제 수행 단계 |
| 기능 유지 | 16.2절 기능의 적용 전후 결과와 지원하지 못한 조건 |

먼저 B가 사전에 정의한 지원 조건에 들어가는지 확인한다. 지원 조건을 만족하는 B에서도 안내 핵심 코드의 변경이 필요하다면 위 핵심 주장은 해당 사례에서 지지되지 않는다. 설정·장면·전처리의 변경은 자동 실패가 아니며, 필요한 작업을 공개하고 재사용 범위에 포함한다. 새 형식 등 지원 조건 밖의 자료는 적용 범위의 한계로 보고한다.

자료 교체 확인이 없으면 결론은 ‘교체를 고려한 구조를 설계했다’로 제한한다. 별도 자료에서 확인되면 ‘해당 자료와 지원 조건에서 핵심 로직의 재사용을 확인했다’까지 서술한다. 다른 지역·전국·임의의 민간 자료로 일반화하지 않는다.

### 16.5 현재 필요한 추가 자료

1. 가까운 유사 연구의 입력·변환·경로 실패 처리·지역 적용 조건에 대한 비교표.
2. 실험 빌드 식별 정보와 실제 도착 반경·갱신 주기·시점 2m 설정 기록.
3. GPS 입력, 요청별 경로 출처·연결 상태, 목적지와 도착 이벤트의 기록. 현재 로그가 위 항목을 모두 제공한다고 확인된 것은 아니므로 추가 수집 방법이 필요하다.
4. 독립 자료 B의 식별 정보와 교체 전후 변경 목록. 확보되지 않으면 확장성은 설계 의도로 유지한다.

이번 보완안은 기능별 판정과 적용 경계를 명확히 하는 단계다. 저널 수준의 기여 여부는 유사 연구 비교와 실제 결과가 갖춰진 뒤 다시 판단한다.

## 17. 기존 연구와 프로젝트를 대조한 보완 포인트 및 결과 입력표

검토일: 2026-10-05. 사용자의 요청에 따라 **기존 연구와의 비교 → 프로젝트에서 구현한 보완 수단 → 성공 판정 → 실측 결과 입력** 순서로 재정리한다. 16절의 재사용 중심 주장은 하나의 후보였으며, 이번 제안에서는 1인칭 시점·경로 표현과 경로 서비스 실패 대응을 주요 검토 대상으로, 자료 교체를 보조 대상으로 둔다. 아직 측정한 개선 결과는 없다.

### 17.1 무엇을 보완했다고 설정할 수 있는가?

| 우선순위 | 기존 연구에서 확인한 내용 | 현재 프로젝트의 대응 구현 | 논문에서 설정할 보완 포인트 |
|---|---|---|---|
| 주요 1 | Aditya 등(2018)은 GPS·MapBox API·OSM LOD1 건물로 구성한 2.5D 지도에서 사용성을 평가했다. 건물 구분과 안내선의 명확성·정확성에 문제가 보고됐다 | GPS 기반 1인칭 시점, 타일 표면 높이 조회, 지형 충돌체를 이용한 경로 높이 투영 | 기존 지도 표시 중심의 평가 범위를 **지표면을 기준으로 시점과 경로를 함께 표시하는 1인칭 구현 및 표현 일관성 검증**으로 확장 |

| 보조 | OpenFLAME(2026)은 독립 지도 서버 발견·연계, 3D 타일 표시, 경로 계산과 위치 추정을 구현한다. 부록에 실내 AR 안내와 이기종 좌표 지도도 다룬다 | SHP·DEM 서버 변환, 지형 소스 선택, CSV 시설물 배치 및 Unity 안내 연결 | **국내 공공자료로 지역 3D 안내 환경을 구성하는 구체적인 적용 절차와 재사용 조건**을 제시. OpenFLAME보다 확장성이 우수하다는 주장은 제외 |

위 표의 ‘보완 포인트’는 원문과 구현의 대조에 따른 제안이다. 기존 연구의 기능 부재나 본 구현의 성능 우월성을 원문만으로 확정하지 않는다. 특히 Aditya 논문의 안내선 문제는 API 장애와 같은 문제가 아니다. 본 프로젝트의 대체 절차도 정상 응답으로 받은 부정확한 API 경로를 자동 검출·수정하는 구조라고 볼 수 없다.

모바일 3D 지도, GPS, 서버·클라이언트 연계 자체는 기존 연구에도 있다. 이를 새 기여로 쓰지 않는다. 보완의 근거는 **현재 구현의 구체적 처리와 그 효과를 분리해 확인한 결과**에 둔다. 새로운 알고리즘을 제안한 것으로 표현하지 않는다.

### 17.2 주요 보완 1: 지표면 기준의 1인칭 시점·경로 표현

연구 주장 후보:

> GPS의 수평 위치를 이용하고 시점·경로의 높이를 표현된 지형 표면에 연결하여, GPS 고도나 고정 높이를 그대로 사용하는 구성보다 지면 관통·과도한 부유와 목표 오프셋의 이탈을 줄일 수 있다.

현재 구현 근거:

- `FirstPersonGPSController.OnGPSPositionUpdated`: 수용한 GPS 입력의 X/Z와 지면 높이 캐시+눈높이를 사용한다. 지면 확보 전에는 GPS Y+눈높이를 사용할 수 있다.
- `SampleAndUpdateGroundHeight`: Cesium 높이 조회 후 실패 시 Raycast를 사용한다. 지면 캐시·보간·재조회 조건이 있으므로 실제 카메라가 모든 프레임에서 즉시 2m를 유지한다고 단정하지 않는다.
- `RouteRenderer.ProjectToRoadSurface`는 현재 실제 코드에서 지형을 먼저 확인하고 도로를 차선으로 확인한다. 최종 경로 정점은 `SnapRouteVerticesToTerrain`에서 지형에 다시 투영한다. 주석과 README의 ‘도로 우선’ 설명은 평가 근거로 쓰지 않는다.
- 지형 스냅 정점만 검사하면 정점 사이 선분의 지면 관통을 놓칠 수 있다. 최종 화면에 표시되는 선분도 검사한다.

비교 조건 제안:

| 조건 | 유지할 항목 | 달리할 항목 |
|---|---|---|
| 카메라 비교 | 동일 GPS 기록·수평 위치·지형·눈높이 2m·보간 및 이상치 처리 | A: GPS Y+2m / B: 현재 지표면 기반 Y+2m |
| 경로 비교 | 동일한 수평 경로·자료·카메라·렌더링 조건 | A: 입력 경로 높이를 유지 / B: 현재 표면 투영 적용 |

이는 동일 프로젝트 안에서 해당 처리를 적용/미적용하는 비교다. 과거 연구 앱을 재현하지 않았으므로 ‘Aditya 앱보다 수치적으로 우수하다’고 서술하지 않는다. 비교 실행 모드와 평가 기록 수집은 현재 자동 제공된다고 확인되지 않았으며 후속 준비가 필요하다.

평가 정의:

- 검사 위치의 기준 지면 높이를 `y_surface`로 기록한다. 사용한 지형 레이어와 타일 상태를 고정하고, 제어에 사용한 캐시값을 그대로 정답으로 복사하지 않는다. 렌더링된 지면과 검사 기준이 다르면 그 조건도 기록한다.
- 카메라 잔차: `e_camera = abs((y_camera - y_surface) - 2.0m)`.
- 경로 잔차: `e_route = abs((y_route - y_surface) - o_route)`. `o_route`는 실험 빌드의 실제 최종 표시 오프셋이다. 현재 소스 기본값 0.05m를 실험값으로 자동 확정하지 않는다.
- 경로는 최종 선분을 1m 간격으로 검사하는 방안을 제안한다. 이는 검사 간격이며 DEM 해상도 90m를 1m로 높인다는 뜻이 아니다.
- 지면 아래로 들어간 표본과, 사전 허용 오차보다 높게 떠 있는 표본의 비율을 계산한다. 카메라는 목표 눈높이, 경로는 목표 표시 오프셋을 각각 기준으로 한다.
- 기준 지면을 찾지 못한 표본은 별도 집계한다. 정상 표본에서 조용히 제외하여 개선율을 높이지 않는다. 초기 로딩·지형 로딩 완료·경사지 조건을 나누어 기록한다.

성공 판정 제안:

1. A와 B의 대응 기록에서 B의 카메라·경로 잔차와 관통/과도한 부유 비율이 줄어들면 해당 항목의 개선을 지지한다. 개선이 없거나 악화된 항목은 개선 주장에 포함하지 않는다.
2. 표현 목표 달성의 예비 기준으로, 지형 로딩 완료 조건에서 카메라 잔차 95백분위 ≤0.20m, 경로 잔차 95백분위 ≤0.10m를 제안한다. **본 연구용 제안값이며 공인 기준이 아니다.** 실험 빌드의 선 두께·보간 조건과 작은 예비 확인을 근거로 채택 또는 조정한 뒤 본 측정 전에 고정한다.
3. GPS 갱신에서 화면 갱신까지의 지연과 지면 조회 실패율도 함께 남긴다. 높이 잔차 감소만으로 위치 추종 전체가 좋아졌다고 판단하지 않는다.

### 17.3 주요 보완 2: 외부 경로 서비스 실패에 대한 지역 경로 계산

연구 주장 후보:

> 지형과 도로 자료가 준비된 실험 지역에서 외부 경로 서비스가 실패하거나 결과를 반환하지 않아도, 도로 메시 또는 NavMesh를 이용해 일부 조건에서 목적지까지 연결된 경로를 확보할 수 있다.

비교 조건은 동일 출발·목적지 쌍에서 A=API 단독, B=현재 단계별 대체 처리로 둔다. 정상 응답, API 오류/빈 결과, 도로 연결 단절, NavMesh 밖 목적지를 구분한다. 지도 타일의 전체 통신까지 차단하는 실험과 API만 실패시키는 실험은 다르다. 현재 시스템의 완전 오프라인 운영을 주장하지 않는다.

기존 연구의 측정치와 직접 비교하기보다, 문헌에서 확인한 서비스 중심 구성에 대해 **자체 구현에서 외부 경로 입력을 단독으로 사용하는 조건과 대체 계산 조건을 비교**한다. 실제 장애·기록된 오류 재생·테스트 조건 주입도 구분한다.

경로 확보의 성공 기준 제안:

1. 출력이 둘 이상의 점이며 출발지·목적지에 연결된다. 평가 전 도로 위의 출발·목적지 좌표를 지정하고, 시작·끝 접속 거리의 예비 허용값은 각각 5m로 제안한다. 도로 그리드 기본 간격 8m와 자동 간격 확대가 접속 오차에 영향을 줄 수 있으므로 적용 조건을 확인한 뒤 본 측정 전에 고정한다.
2. 최종 표시 경로의 각 선분을 검사했을 때 사전 정의한 허용 도로/이동 영역을 벗어나거나 장애물을 가로지르는 구간이 없어야 한다. 1m 간격 표본 검사와 영상/자료 확인을 함께 제안한다. 점 검사만으로 모든 선분의 수학적 안전성을 입증했다고 쓰지 않는다.
3. 부분 NavMesh 경로+직선 접속, 전체 직선 대체, 도로 영역 밖 접속은 따로 기록한다. 허용 이동 영역과 연결성을 확인하지 못한 직선은 유효 경로 확보의 성공 수에 포함하지 않는다.
4. 경로 생성 출처와 최종 표시 경로를 모두 확인한다. `RouteRenderer.BuildRoadRoute`도 구간별 NavMesh로 수평 형상을 바꿀 수 있어, `NavigationService.CurrentRoute`만 평가하면 사용자가 실제로 본 경로와 달라질 수 있다.
5. API 실패 조건에서 B의 유효 경로 확보율이 A보다 높으면 실패 대응의 효과를 지지한다. 연결되지 않은 직선 표시만 늘어나면 그 주장은 지지되지 않는다. 정상 조건의 성공률·지연 악화도 함께 제시한다.

현재 보완해야 할 기록·판정 사항: `OnRouteCalculated`는 직선에도 발생하고, 부분 경로도 반환한다. `EffectiveNavMeshSampleRadius`는 최소 1000m여서 멀리 떨어진 도로로 접속할 수 있다. 동일 목적지의 주기 갱신 요청에는 응답 역전 검토가 필요하다. 이는 측정 조건이나 실패 분석에 포함하며 현재 실제 실패가 발생했다는 확정 진술은 아니다. API 경로는 자동차 경로 입력이므로 이 검증만으로 보행 최적 경로나 실제 보행 안전성을 주장하지 않는다.

### 17.4 보조 기여: 국내 공공자료의 구축·교체 절차

논문에서 쓸 수 있는 기여 문장 후보:

> 국내 공공 SHP·DEM과 시설물 자료를 지역 3D 안내 환경에 적용하는 절차를 구성하고, 자료 교체 시 재사용되는 안내 로직과 수정이 필요한 설정·장면·전처리의 범위를 확인하였다.

마지막 ‘확인하였다’는 실제 교체 후에 사용한다. OpenFLAME보다 공간자료 연계·확장성이 개선됐다는 뜻은 아니다. 해당 원문은 독립 지도 관리와 좌표계가 다른 지도 연결을 이미 다루므로, 본 프로젝트에서는 자체 공공자료 구축 사례와 실무 적용 조건을 보조 기여로 제시한다.

성공 기준은 지원 조건을 사전 정의한 독립 자료 B를 적용하여 해당 자료 범위에서 GPS·목적지·안내 상태 핵심 소스 변경 0건, 자료 로드 및 해당 기능 유지가 확인되는 것이다. 설정·장면·전처리는 바뀔 수 있으며 실제 변경 목록과 소요시간을 기록한다. 건물 자료만 교체했다면 건물 자료 적용과 관련 기능에 대해서만 결론을 낸다.

### 17.5 본문에 넣을 핵심 주장과 현재 남은 작업

권장 기여 구성: **지표면 기준 GPS 연동 1인칭 시점·경로의 표현 일관성**, **외부 경로 서비스 실패 시 지역 자료를 이용한 대체 계산**, **공공자료 적용·교체 절차의 조건과 한계**.

17.2~17.4절의 기준값은 제안이며 이미 확정한 합의나 실측 결과가 아니다. 시점 2m와 DEM 90m는 기존 사용자 지정 조건으로 유지한다. 상세 반복 수·비교 실행 모드·로그 수집·본 측정 전 기준 고정은 후속 준비가 필요하다. 실제 숫자를 채우기 전에 이 준비를 완료해야 비교 결과를 해석할 수 있다.

이번 검토는 기존 원문과 현재 소스를 읽어 작성한 연구 구성안이다. 실험을 수행하거나 코드·실험 빌드를 변경하지 않았다. 서로 다른 연구의 적용 초점을 연결해 보완안을 설정한 것이며, 모든 관련 연구에 대한 신규성 증명이나 저널 채택 보장은 아니다.

## 18. 독자가 납득할 비교군과 최소 비교값

### 18.1 권장 비교군

효과를 주장하는 처리만 달리하고 입력·자료·단말을 맞춘 자체 비교를 권장한다. 기존 연구의 실험 수치를 대전 사례의 실측값과 그대로 비교하는 방법은 지역·자료·단말·과제 차이를 분리하지 못한다. 17절의 원문은 관련 연구와 적용 범위 비교의 근거로 사용하고, 자체 처리 효과는 아래 비교로 확인한다.

| 검토 대상 | 비교군 | 제안 구성 | 최소 비교값 |
|---|---|---|---|
| GPS 고도를 대신하는 시점 처리 | 기록된 GPS 고도+눈높이 2m | 표현된 지면 높이+눈높이 2m | 목표 눈높이 잔차의 평균·95백분위, 지면 관통/과도한 부유 비율 |
| 별도 도로 메시와 지형을 연결하는 경로 표시 | 도로 메시 표면에 투영 | 지형 표면에 투영 | 표시 경로의 지면 기준 잔차 평균·95백분위, 관통/과도한 부유 비율, 표면 조회 실패 비율 |
| 단계별 대체 계산의 효과 | A: API 단독, B: API+NavMesh | C: API+도로 메시 A*+NavMesh | 유효 경로 확보율, 부분·직선 대체·실패 비율, 처리 지연 평균·95백분위 |

시점 비교는 실제 문제였던 GPS 고도 사용과 대비하는 직접적인 비교다. 추가로 현재 높이 조회 절차 자체의 장점을 주장한다면 Raycast 단독과 현재 Cesium 조회→Raycast 절차를 비교한다. 이때 캐시·보간·조회 주기는 공통으로 두고 높이 취득 절차만 바꾼다. 이 추가 비교 없이 Cesium 조회 절차가 일반적인 지면 조회보다 우수하다고 주장하지 않는다.

경로 비교는 고정 0m 표시보다 실제 도로 메시 표면을 사용하는 구성이 더 유용한 비교군이다. 양쪽에 같은 표시 오프셋을 주고, 수평 경로·선분 분할·NavMesh 보정·선 두께를 공통으로 둔다. 고도 0m 입력은 별도의 단순 미처리 참고 조건으로 둘 수 있지만 그것만 이겼다는 결과로 처리 방법의 강점을 크게 주장하지 않는다.

경로 계산에서 A와 C만 비교하면 API 실패 시 A의 경로가 없는 것은 구조적으로 예상되는 결과다. **B와 C도 비교해야 자체 도로 메시 A*가 NavMesh만 사용한 대체 처리에 무엇을 추가했는지 확인할 수 있다.** B와 C가 같다면 다층 구성의 구현 사실을 설명하고 A*에 의한 추가 개선은 주장하지 않는다.

### 18.2 성공 해석과 공정한 조건

1. 시점·경로의 잔차는 표현된 지면과 목표 오프셋의 차이로 정의한다. 처리에 쓰인 캐시값을 그대로 정답으로 쓰지 않고, 같은 시각·위치의 렌더링 지면을 검사한다. 실제 고도·GPS 측정 정확도의 향상으로 해석하지 않는다.
2. 경로 높이 비교는 정점뿐 아니라 최종 선분도 검사한다. 표면을 찾지 못한 표본의 수와 비율도 보고한다. 지형에 투영하면 지형 잔차가 줄어드는 것은 예상되는 결과이므로, 실제 관통·부유 감소와 로딩/경사지 실패 조건을 함께 보여준다.
3. 유효 경로는 출발·목적지 접속, 연결성, 사전 정의한 허용 영역 조건을 모두 확인한 완전 경로로 집계한다. 직선 표시나 NavMesh 부분 경로를 완전 경로 수에 합산하지 않는다. 17절의 기준을 공통으로 적용한다.
4. API 정상과 실패 조건을 모두 비교한다. NavMesh가 정상 연결된 사례, NavMesh는 불완전하지만 도로 메시에는 경로가 있는 사례, 양쪽 모두 연결되지 않은 사례를 포함한다. 특정 방법이 잘되는 사례만 고르지 않고 선정 근거를 남긴다.
5. 경로 생성 지연은 API 오류 확정 후 최종 경로 확보까지와, 최초 요청부터 결과 적용까지를 구분한다. 타임아웃이나 API 대기 시간만 달라 생긴 차이를 A* 계산 성능으로 설명하지 않는다.
6. GPS 기록·출발/목적지·단말·DEM 90m·시점 2m·자료 버전·타일 로딩 상태를 공통으로 둔다. 반복 수와 실행 순서를 기록한다. 독립 경로별 결과를 제시하고 프레임 수를 독립 실험 횟수로 취급하지 않는다.

주요 결과값은 평균 하나보다 **평균+95백분위**, 비율은 **성공 수/전체 수와 백분율**, 개선은 **조건 간 차이**로 보고한다. 95백분위는 표본의 95%가 그 값 이하라는 뜻이며 평균이 숨기는 큰 이탈·긴 지연을 보여준다. 확보율 차이는 퍼센트포인트(%p)로 표시한다. 대응 실험의 반복 변동도 함께 기록한다.

17절의 카메라 0.20m·경로 0.10m·접속 5m는 아직 채택되지 않은 예비 판정값이다. 이를 보편적인 합격 기준으로 사용하지 않는다. 본 측정 전에 표현 목적·선 두께·그리드 간격과 예비 확인 근거로 허용값을 정하고, 실제 결과를 보고 유리하게 바꾸지 않는다.

## 19. 독자적 프로젝트를 기존 연구와 연결하는 시사점

### 19.1 사용자 요청에 따른 연구 축 정리

본 프로젝트는 기존 논문의 실험 방법을 그대로 재현해 진행한 연구가 아니다. 사용자가 독자적으로 진행한 **3D 지도 환경의 1인칭 내비게이션**과 **공간데이터의 추가·교체 및 확장 활용**을 두 연구 축으로 유지한다. 17~18절의 지면 처리·대체 경로 비교는 이 두 축을 뒷받침할 세부 검증 후보이며, 연구 주제를 해당 처리의 성능 개선으로 자동 변경하는 제안은 아니다.

기존 연구와의 비교 목적은 본 구현의 관심사와 적용 조건을 학술적 맥락에 놓고, 사례에서 얻을 수 있는 설계·적용 지식을 설명하는 것이다. ‘관련 연구 → 독자적 구현 사례 → 그 사례가 드러낸 조건과 한계 → 시사점’의 순서로 서술한다. 관련 연구와 다른 구현이라는 사실만으로 최초성이나 우월성이 성립하는 것은 아니다.

우측 시사점은 원문과 프로젝트 구현을 대조한 해석·제안이다. 기존 연구가 해당 모든 조건을 무시했다거나, 본 프로젝트만 처음 다룬다고 뜻하지 않는다. OpenFLAME은 이기종 좌표계와 지도 구축 도구도 다루므로 단순히 ‘자료 확장이 된다’를 그 연구 대비 새 기여로 제시하지 않는다.

### 19.3 두 연구 축에서 도출할 구체적인 시사점

#### 1. 1인칭 내비게이션: 공공 공간자료의 이용 형태와 연결 조건

제시할 내용은 ‘공공자료로 건물을 화면에 표시했다’에서 더 나아가, GPS 기반 사용자의 위치·시점·목적지·경로·도착 상태를 연결한 제한 지역의 스마트폰 적용 사례다. 공간자료가 실제 안내 기능에서 어떤 역할을 맡고 어떤 준비를 필요로 하는지 설명한다.

현재 구현에서는 지형은 시점과 경로의 표면 기준, 도로 메시는 탐색 영역, 건물·시설물은 공간 표현을 구성한다. 원래 자료의 역할과 안내 애플리케이션에서의 역할을 구분한 데이터 흐름표가 기여의 근거가 된다. 이를 통해 후속 구현자가 같은 종류의 자료를 안내 환경에 적용할 때 필요한 구성과 제약을 파악할 수 있다.

뒷받침할 자료: 자료별 역할·변환 흐름, GPS에서 화면·경로·도착까지의 연결 기록, 실제 단말 영상·로그, 정상/실패 조건. 시야·방향 이해·편의성 향상은 사용자 평가 결과가 있을 때 별도 시사점으로 추가한다.

#### 2. 공간데이터 확장 활용: 자료 준비와 안내 기능 유지의 구분

현재 지형 소스 선택, SHP/DEM 변환, CSV 시설물 배치 구조는 자료를 추가·교체하는 설계 근거가 된다. 자료를 불러온 뒤 안내 기능에서 사용하는 데에는 입력 속성, 좌표 변환, 충돌체·레이어, 도로 연결성, NavMesh 및 장면 참조 등의 조건이 남는다.

따라서 확장 활용의 시사점은 ‘전국 어디든 바로 동작한다’가 아니라 **새 자료를 안내 환경에 적용할 때 재사용되는 구성과 다시 준비해야 하는 구성의 경계를 설명한다**는 것이다. 실제 교체 전에는 구조 분석에서 확인한 의존 조건을 제시하고, 교체 후에는 유지·변경 기록으로 해당 자료에서의 재사용 범위를 보고한다.

뒷받침할 자료: 지원 입력 조건표, 독립 자료 추가/교체 기록, 전처리·설정·장면·코드 변경 목록, 변경 후 기능 확인. 민간 자료나 다른 지역을 실제 적용하지 않았다면 해당 적용 결과는 미검증으로 남긴다.

#### 3. 두 축의 결합: 데이터 확장을 안내 환경의 재사용으로 연결하기

이 사례에서 함께 검토할 질문은 **‘자료를 추가·교체했을 때 1인칭 안내의 어떤 기능을 유지할 수 있고, 어떤 부분을 다시 준비해야 하는가?’**이다. 3D 자료의 로드와 안내 환경 적용을 구분하여 평가하는 관점을 제시한다.

자료별 적용 조건과 안내 기능별 조건을 연결한 표를 만들고, 유지된 기능 및 실패 원인을 남기면 개별 프로젝트가 다른 구현자가 참고할 수 있는 적용 지식을 제공한다. 지면 처리나 경로 대체 실험은 해당 연결을 설명하는 세부 근거로 선택한다. 특정 기능 비교를 두 연구 축의 대체 주제로 만들지 않는다.

### 19.4 논문에서 사용할 기여 문장 후보

> 본 연구는 국내 공공 공간자료와 GPS를 연계한 스마트폰 1인칭 3D 내비게이션의 지역 적용 사례를 제시한다. 지형·도로·건물·시설물 자료의 처리 흐름과 안내 기능의 연결 구조를 기술하고, 자료의 추가·교체를 고려할 때 재사용할 수 있는 구성과 별도 준비가 필요한 조건을 정리한다. 이를 통해 공공 공간자료를 사용자 위치 기반 안내 환경으로 활용하는 데 필요한 설계·적용 지식을 제공한다.

이 문장은 현재 연구의 위치를 설명하는 후보이며, 실측 결과가 없는 개선 효과나 자료 교체 완료를 포함하지 않는다. 기존 방법을 충실히 재현하지 않아도 적용 사례와 그 조건을 제시할 수 있다. 졸업논문에서는 이 방향으로 목적·기여를 구성할 수 있으며, 저널 수준의 신규성 판단은 사례의 결과가 제공하는 새 지식과 기존 연구의 중복 범위를 추가로 확인해야 한다.

## 20. 앱 배포 없이 수행할 실효성 평가와 설문 비교

### 20.1 평가 목적과 제약

사용자는 보안상 앱 배포가 어렵고, 동영상 또는 앱 실행 화면을 보여주는 대면 평가를 고려하고 있다. 이 조건을 유지한다. 연구자가 제공하는 단말의 직접 조작은 허용되는 경우에만 선택지로 제안하며 필수로 요구하지 않는다.

설문은 체감 유용성·만족·선호·이용 의향에 적합하다. 실제 효과성은 과제 성공률과 오류, 효율은 과제 수행시간 등의 관찰값으로 평가할 수 있다. 어느 하나가 모든 실효성을 대표하지 않는다. [NIST 사용성 평가 설명](https://www.nist.gov/programs-projects/usability-testing)

본 연구의 두 축은 별도로 평가한다. 1인칭 안내의 정보 전달·사용 경험은 참여자 과제와 설문으로, 공간자료 확장 활용은 자료 교체·변경 목록·기능 유지 기록으로 뒷받침한다. 비개발자의 영상 만족도는 자료 호환성·지역 확장성의 검증 근거로 사용하지 않는다.

### 20.2 가능한 방법과 해석 범위

| 방법 | 얻을 수 있는 근거 | 설문과 비교한 장점 | 한계 및 논문 표현 |
|---|---|---|---|
| 동영상 시청 후 설문 | 체감 명확성, 예상 유용성, 선호, 사용 의향 | 많은 참여자에게 동일한 자극을 제시하기 쉬움 | 실제 조작·보행 경험 없음. ‘영상 기반 인식·수용성 평가’로 기술 |
| 연구자 실시간 시연 후 대면 설문 | 기능 이해, 시연 기반 인상, 질문에서 드러나는 문제 | 원하는 장면을 확인하고 후속 이유를 들을 수 있음 | 연구자의 설명·유도, 참여자별 시연 차이와 면대면 긍정 응답 가능성. 직접 사용 평가와 구분 |
| 영상/화면을 이용한 판단 과제+설문 | 이동 방향·목적지 등의 정답률, 응답시간, 체감 명확성 | 주관적 인상에 실제 판단 결과를 추가. 배포·앱 조작 없이 가능 | 화면의 정보 전달을 평가하며 실제 보행 도착률이나 앱 조작성을 입증하지 않음 |
| 연구자 단말에서 참여자 직접 조작+설문 | 목적지 선택·안내 시작·취소·시야 변경의 성공률, 시간, 실수·도움 요청 | 직접 수행의 성공과 체감을 함께 확인. 앱 공개 배포 불필요 | 단말 접근이 허용되는 경우에만 가능. 실내 조작 과제가 실제 현장 보행 효과를 대신하지 않음 |
| 구현 로그·자료 적용 실험 | 위치/경로 갱신, 도착 판정, 자료 교체 후 기능 유지·변경 작업 | 기술적 동작과 확장 활용의 근거 제공 | 사용자의 이해·편의성·만족과 별도의 평가 축 |

연구자 시연을 보는 것과 참여자가 직접 조작하는 것은 다르다. 대면이라는 이유만으로 영상 설문보다 근거가 강해지는 것은 아니다. 과제 수행과 관찰을 포함하는지, 무엇을 평가하는지가 중요하다. 직접 수행 과제의 구성 근거는 [GOV.UK의 진행자 동반 사용성 평가 안내](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing)에서 확인할 수 있다.

### 20.3 현재 제약에서 권장하는 조합

**영상/실행 화면 판단 과제 + 과제 후 짧은 설문 + 기존 기술·자료 적용 기록**을 권장한다. 직접 단말 조작이 가능하면 조작 과제를 추가한다. 단순 시청 설문만 가능한 경우에도 시행할 수 있지만 결론을 예상 유용성·수용성에 한정한다.

판단 과제 제안:

1. 교차로 진입 직전 영상을 멈추고 ‘이 화면에서 어느 방향으로 진행해야 하는가?’를 묻는다.
2. 목적지 부근 화면에서 ‘표시된 목적지는 어느 건물/지점인가?’를 묻는다.
3. 사전 정의한 현재 위치·경로 관계를 판단하게 한다. 자극에 그 판단을 위한 정보가 실제 포함되어 있어야 한다.

각 과제에는 자료·경로와 일치하는 사전 정답을 마련하고, 선택지와 응답 제한시간·재생/다시 보기 규칙을 동일하게 적용한다. 이후 프레임에서 정답이 드러나기 전에 응답을 받는다. 과제 소개 단계에서 정답을 암시하지 않는다.

측정값:

- 정답률 = 정답 수 / 판단 과제 수. 무응답·시간 초과는 별도 기록하고 분모에서 조용히 제외하지 않는다.
- 응답시간 = 질문과 판단 화면이 제시된 시점부터 응답까지. 오답·무응답과 정답 응답의 시간을 구분하며 빠른 오답을 효율 향상으로 해석하지 않는다.
- 과제별 확신도·정보 명확성·예상 유용성·선호를 설문으로 수집한다. 실사용을 전제로 한 문항은 시청 평가에 맞지 않을 수 있다.
- 표준 사용성 척도를 수정하거나 시청만 한 참여자에게 사용한 경우, 원 척도와 동등한 실사용 평가로 자동 해석하지 않는다. 실제 수행하지 않은 작업의 용이성은 ‘예상’ 평가임을 밝힌다.

비교를 추가한다면 동일 장소·경로·목적지 정보의 조감도 지도 화면과 1인칭 화면을 고려할 수 있다. 다른 표지·확대 수준·영상 길이 등에서 정보량이 달라지지 않도록 비교 목적에 맞게 맞춘다. 자체 조감도 화면을 썼다면 상용 2D 지도 전체와의 비교라고 쓰지 않는다.

같은 문제를 두 번 보여주면 정답을 기억할 수 있다. 동등한 난이도의 여러 구간을 구성하고 화면 조건·구간 배정을 교차하여 순서·기억 효과를 줄인다. 지역 친숙도와 지도 사용 경험을 기록하고, 참가자별 결과를 분석 단위로 제시한다. 한 참가자의 많은 문항을 독립 참가자 수처럼 취급하지 않는다.

### 20.4 결과의 해석

| 관찰 결과 | 지지되는 해석 |
|---|---|
| 만족·유용성 점수만 높음 | 해당 영상/시연에 대한 긍정적인 인식·수용성 |
| 정답률이 높아지고 응답시간이 유지·감소 | 해당 조건에서 화면을 통한 방향/목적지 판단의 효과성·효율이 개선됨 |
| 설문은 긍정적이나 판단 오류가 많음 | 긍정적인 인상과 실제 판단 결과가 일치하지 않음. 표시 개선 필요 |
| 단말 직접 조작에서 성공률·시간이 개선 | 평가한 조작 과제의 사용성 개선. 현장 보행 성과와 구분 |
| 자료 교체 후 기능 유지와 변경 범위 확인 | 해당 자료·조건에서의 재사용 범위 확인. 참여자 선호와 별도 근거 |

이 조합은 배포 제약 안에서 가능한 평가 제안이다. 참여자 모집·평가·실측은 수행하지 않았으며, 표본 수·최종 문항·자극 제작·대조 조건은 후속 설계 대상이다. Aditya 등(2018)의 평가는 현장 과제와 기록도 포함하므로 그 연구를 ‘설문만으로 실효성을 입증한 사례’로 인용하지 않는다. [Aditya 등 원문](https://isprs-archives.copernicus.org/articles/XLII-4-W10/3/2018/isprs-archives-XLII-4-W10-3-2018.pdf)

## 21. 주제·기여·실측·비교·실효성 근거의 종합안

### 21.1 전반적인 주제와 연구 목적

권장 제목: **공공 공간데이터 기반 Cesium 스마트폰 1인칭 3D 내비게이션의 설계 및 구현: 데이터 확장 활용과 유성구 적용 사례**.

제목은 종합에 따른 권장안이다. 본 연구는 기존 논문의 실험 방식을 그대로 재현한 것이 아닌 독자적 시스템 구현 사례이며, 두 축은 **3D 지도 환경의 1인칭 내비게이션**과 **공간데이터의 추가·교체 및 확장 활용**이다.

연구 목적: 지형·도로·건물·시설물 자료와 GPS를 연계한 스마트폰 1인칭 안내 환경을 구성하고, 제한된 지역에서 기능 연결과 정보 전달을 평가하며, 추가 자료를 적용할 때 재사용되는 구성과 다시 준비해야 하는 조건을 설명한다.

현재 조건은 유성구의 실제 구현 범위, DEM 90m, 실험 시점 2m다. 도로 메시의 고정 1m는 생성 설정값으로, 실제 도로 표고나 눈높이로 해석하지 않는다. DEM 수직 기준은 미확인이며 절대 표고 정확도 향상을 주장하지 않는다. 스마트폰 실행은 사용자 확인 사항이고, 정량 실측 및 참여자 평가는 아직 결과가 없다. 민간 자료·다른 지역·스마트 글래스는 확인한 범위 밖의 확장 가능성으로 둔다.

### 21.2 내세울 포인트와 시사점

1. **1인칭 안내의 적용 사례:** GPS 위치, 카메라 시점, 목적지, 경로, 도착 상태를 하나의 스마트폰 안내 흐름으로 연결한 설계와 실제 적용 조건을 제시한다.
2. **공공 공간자료의 역할별 연계:** 지형은 표면 기준, 도로 메시는 탐색, 건물·시설물은 공간 표현에 활용하는 데이터 처리 흐름을 설명한다.
3. **확장 활용의 조건과 경계:** 지원 자료의 추가·교체에서 안내 로직의 재사용과 전처리·설정·장면 작업의 변경 범위를 구분한다. 실제 교체 기록이 없으면 설계 조건과 의도로 한정한다.

관련 연구와의 연결은 19절의 Aditya·MoNa3D·OpenFLAME 비교를 사용한다. 기여는 국내 공공자료로 안내 환경을 구성하는 재현 가능한 적용·설계 지식에 둔다. 코드에 존재하는 기능을 나열하는 데 그치지 않고 입력 조건, 정상/실패 사례, 유지·변경 내용을 연결한다. 기존 연구보다 사용성이 우수하다거나 새로운 탐색 알고리즘을 제안했다는 뜻은 아니다.

### 21.3 주장을 뒷받침하기 위해 필요한 핵심 평가

| 평가 축 | 확인/측정할 것 | 비교 구성 | 입증 자료 |
|---|---|---|---|
| 기능 연결 | 유효 GPS 취득·위치/시점 갱신, 목적지 변경 후 경로 갱신, 종점 연결, 설정 반경의 도착 이벤트 | 정상·실패·경계 조건과 사전에 정한 기대 결과 | 실험 빌드 정보, 입력/출력 로그, 실행 영상, 성공·실패·누락·중복 기록 |
| 1인칭 정보 전달 | 방향·목적지 판단의 정답률, 응답시간, 무응답/오류 | 동일 장소·목적지 정보의 자체 조감도 화면과 1인칭 화면 | 비교 자극 영상/화면, 사전 정답, 참가자별 응답과 시간, 순서·구간 배정 |
| 체감 유용성 | 정보 명확성, 예상 유용성, 선호·이용 의향과 이유 | 판단 과제 후 각 화면 조건의 설문 | 설문지, 비식별 응답, 점수 분포·자유 의견 |
| 자료 확장 활용 | 지원 조건 내 독립 자료 추가·교체 후 기능 유지, 코드/설정/장면/전처리 변경 | 기존 자료 A와 독립 자료 B의 적용 전후 | 자료 식별정보·범위·속성·좌표계, 변환/적용 기록, 변경 목록, 확인 결과 |

1인칭과 조감도의 비교는 화면의 정보 전달 효과를 평가하는 제안이다. 연구자가 가진 단말의 직접 조작이 허용되면 목적지 선택·안내 시작 등의 성공률·시간·실수 관찰을 추가할 수 있다. 앱 배포는 이 평가의 필수 조건이 아니다. 영상·시연만으로 실제 보행 도착률·조작 편의성 향상을 검증했다고 서술하지 않는다.

자료 교체는 다른 지역 전체를 새로 구현해야만 가능한 것은 아니다. 동일 대상 지역의 내용이 다른 독립 자료를 추가·교체할 수 있다. 이 결과는 해당 자료 유형과 지원 조건의 재사용 근거이며 전국 운영성을 의미하지 않는다. 한 종류만 교체했다면 전체 데이터 계층을 교체한 것으로 쓰지 않는다.

### 21.4 개선 효과를 주장할 경우의 보조 비교

| 개선 주장 | 비교군 | 기록값 |
|---|---|---|
| 지표면 기준 시점의 표현 일관성 | 동일 GPS 기록에서 GPS 고도+2m / 지형 높이+2m | 목표 높이 잔차 평균·95백분위, 관통·과도한 부유 비율, 지면 미확보 비율 |
| 경로의 지형 표면 일치 | 동일 수평 경로와 표시 오프셋에서 도로 메시 표면 투영 / 지형 표면 투영 | 경로 잔차 평균·95백분위, 선분 관통·부유 비율, 표면 조회 실패 |
| 외부 경로 서비스 실패 대응 | API 단독 / API+NavMesh / API+도로 메시 A*+NavMesh | 유효 경로 확보 수/전체 수, 부분·직선 대체·실패 수, 처리 지연 평균·95백분위 |

이 비교들은 프로젝트 내부의 처리 효과 확인이며 기존 논문 방식의 정확한 재현이 아니다. 결과에 맞춰 ‘해당 기준 구성 대비 개선’이라고 표현한다. 각 개선을 본문의 성과로 주장하는 경우 수행하고, 모든 보조 비교를 논문의 필수 실험으로 만들지 않는다.

경로의 완전·부분·직선 대체를 구분한다. 경로 계산 이벤트나 선의 표시만으로 완전 경로 확보를 인정하지 않는다. 입력 경로와 `RouteRenderer`가 실제 표시한 경로의 차이도 기록한다.

### 21.6 결과표의 최소 구성

- 기능별 정상/실패 조건의 시도 수·성공 수·실패 원인 표.
- 조감도/1인칭 판단 과제의 참가자별 정답률·응답시간 및 조건 차이 표.
- 조건별 설문 분포와 예상 유용성·명확성·선호, 자유 의견 표.
- 독립 자료 교체 전후의 유지 구성·변경 작업·기능 결과 표.
- 선택한 보조 개선 주장에 대한 기준 구성/현재 구성의 실측값과 차이 표.

21절은 지금까지의 연구 구성과 평가 후보를 종합한 제안이다. 구현 관찰, 기술 실측, 참여자 평가, 자료 교체 검증을 구분하며 아직 수집하지 않은 자료가 확보된 것으로 서술하지 않는다.

## 22. 건물·지형·지표면 이미지와 공간·방향 인식 관련 문헌

검색·검토일: 2026-10-05. 기존 두 연구 축 중 1인칭 화면의 정보 전달 평가에 연결되는 문헌이다. 연구 주제를 변경하거나 이 문헌의 처리 방식을 재현했다고 주장하는 근거가 아니다.

### 22.1 요소와 인식 과제의 구분

- 건물: 주변 위치를 대조하는 랜드마크, 교차로 구분, 목적지 방향 판단. 건물은 시각적 단서이면서 다른 단서를 가리는 요소이기도 하다.
- 지형: DEM이 만드는 지표면 형상. 경사·오르막 방향·능선·골짜기·고도 변화 판단.
- 지표면 이미지: 지형 위에 입히는 일반지도·항공/위성영상. 도로·녹지·수면 등 지표면 특징 구분. 건물 외벽 텍스처와 구분한다.

프로젝트에는 `VWorldOverlayController`의 Base/Satellite 표시와 표시 활성화, `TerrainSourceSwitcher`의 지형 소스 선택이 있다. 건물 모델, 지형 형상, 지표면 이미지는 서로 다른 표현 요소로 구분할 수 있다. 해당 기능을 이용한 참여자 실험이나 효과 검증은 아직 수행하지 않았다.

### 22.2 우선 검토할 논문 6편

**1. 건물·랜드마크 가시성 — Delikostidis 등 (2013)**

Increasing the Usability of Pedestrian Navigation Interfaces by means of Landmark Visibility Analysis. *The Journal of Navigation*, 66(4), 523–537. DOI: 10.1017/S0373463313000209.

[출판사 원문](https://www.cambridge.org/core/journals/journal-of-navigation/article/increasing-the-usability-of-pedestrian-navigation-interfaces-by-means-of-landmark-visibility-analysis/D1E25BB3F5BFE4C4188197F68C2D2E59)

3D 도시 모델로 랜드마크 가시성을 계산하고 모바일 지도에 표시했다. 24명의 현장 방향·내비게이션 과제를 LandNavin과 Google Mobile Maps에서 비교했다. 전체적으로 더 짧은 평균 과제 시간과 높은 완료율을 보고했고, 21명이 가시성 기능을 유용하게 평가했다. 단, 지도 방향·제어 등 다른 기능도 다른 인터페이스 비교이며 논문도 주로 정성적 사용성 근거를 목적으로 한다. 따라서 개선을 건물 추가 하나의 효과로 분리해 인용하지 않는다. 본 프로젝트에는 건물의 존재뿐 아니라 사용자의 시야에서 구분 가능한지 확인할 근거로 연결한다.

**2. 건물 표현과 방향 지식 — Kapaj, Hilton, Lanini-Maggi, Fabrikant (2024)**

The influence of landmark visualization style on task performance, visual attention, and spatial learning in a real-world navigation task. *Spatial Cognition & Computation*, 24(4), 227–267. DOI: 10.1080/13875868.2024.2328099.

[출판사 원문](https://doi.org/10.1080/13875868.2024.2328099) · [저자 공개 PDF](https://akapaj.github.io/publication/kapaj-influence-2024/kapaj-influence-2024.pdf)

46명이 모바일 지도에 표시된 추상적 3D 건물과 사진 텍스처가 있는 사실적 3D 건물을 이용해 현장 경로를 따라갔다. 랜드마크·경로 방향 기억, 건물 순서, 건물 간 거리·방향 판단과 시선을 평가했다. 사실적 표현은 낮은 공간 능력 참가자의 일부 공간 지식에 도움이 되었지만 이동 완료시간의 유의한 차이는 없었다. 사실적 표현 선호와 수행 개선을 구분해야 한다. 건물 유무 비교가 아니며, 외벽 사진의 효과를 지표면 영상의 효과로 옮겨 해석하지 않는다.

**3. 경사와 방향 판단 — Nardi, Meloni, Orlandi, Olivetti-Belardinelli (2014)**

Where is uphill? Exploring sex differences when reorienting on a sloped environment presented through 2-D images. *Perception*, 43(4), 249–264. DOI: 10.1068/p7622.

[소속 대학 연구 기록·초록](https://iris.uniroma1.it/handle/11573/785533)

실내·실외 가상 경사 환경을 여러 방향의 화면 이미지로 보여주고 오르막 방향을 지목하게 했다. 정확도·응답시간·시선을 평가했으며, 주된 연구 질문은 성별 차이였다. 본 프로젝트에는 영상/화면만으로도 경사 방향을 정답이 있는 과제로 평가할 수 있다는 방법상의 근거로 연결한다. 평면과 DEM의 비교나 DEM 추가 효과를 검증한 연구는 아니다. 이 항목은 대학의 초록을 확인한 범위로 정리했다.

**4. 지형 형상 인식 — Kubíček 등 (2019; 온라인 최초 공개 2017)**

Identification of altitude profiles in 3D geovisualizations: the role of interaction and spatial abilities. *International Journal of Digital Earth*, 12(2), 156–172. DOI: 10.1080/17538947.2017.1382581.

[출판사 원문](https://doi.org/10.1080/17538947.2017.1382581) · [소속 대학 서지 기록](https://is.muni.cz/publication/1391578/cs)

39명의 학생이 3D 지형의 두 지점 사이에 맞는 고도 단면을 선택했다. 단안/입체 표시와 정적/상호작용 조건을 비교하여 정답률 등을 평가했다. 상호작용 수준은 평가 결과에 영향을 주었고 입체 표시 자체의 효과는 명확하지 않았다. 본 프로젝트에는 경사·고도 변화 판단 과제를 구성할 근거로 연결한다. 논문의 단안 원근 3D도 일반적인 3D 화면이며, 논문의 'pseudo 3D' 용어를 프로젝트가 3D가 아니라는 의미로 사용하지 않는다. 원자료 5m, 수직 과장과 상호작용 조건이 본 프로젝트의 90m DEM·2m 시점과 달라 성과를 직접 전이하지 않는다.

**5. 지표면 이미지와 경로 인식 — Dillemuth (2005)**

Map Design Evaluation for Mobile Display. *Cartography and Geographic Information Science*, 32(4), 285–301.

[ETH Zürich에서 제공하는 논문 원문 PDF](https://www.raubal.ethz.ch/Courses/geog596/Dillemuth_MapDesignEvaluationForMobileDisplay_05%402010-03-30T23%3B17%3B38.pdf)

28명이 항공사진과 그 사진에서 도로·건물·녹지 등을 단순화한 지도를 소형 화면으로 보며 현장 경로를 따라갔다. 완료시간·오류·확대 조작을 기록했다. 단순화 지도는 더 짧은 완료시간과 적은 확대 조작을 보였고, 항공사진이 오류를 줄인다는 가설은 지지되지 않았다. 사진의 세부 정보가 항상 내비게이션 성과를 높이지는 않는다는 근거다. 2D 지도·GPS 위치 표시 없는 조건이며 본 프로젝트의 1인칭 지표면 텍스처 유무 비교와 동일하지 않다. VWorld 일반지도와 위성영상을 비교할 경우 유용하지만, 일반지도의 라벨·색·기호 차이를 사진 텍스처 하나의 차이로 해석하지 않는다.

**6. 지형과 이미지 계층의 결합 — Douglass, Fish (2022)**

That’s a Relief: Assessing Beauty, Realism, and Landform Clarity in Multilayer Terrain Maps. *Cartographic Perspectives*, (100), 45–66. DOI: 10.14714/CP100.1727.

[출판사 서지·초록](https://cartographicperspectives.org/index.php/journal/article/view/1727) · [출판사 원문 HTML](https://cartographicperspectives.org/index.php/journal/article/download/1727/2093?inline=1)

음영기복 3종과 고도 색상·토지피복·정사영상 3종을 결합한 지도를 비교하여 아름다움·사실성·지형 명확성의 주관적 점수를 평가했다. 정사영상은 아름다움·사실성에서 높게 평가되었으나 지형 명확성 점수에는 주제 이미지보다 음영기복의 영향이 컸다. 화면의 사실성과 지형을 구분하기 쉬운 정도를 별도 문항으로 평가할 근거다. 3D DEM 메시 유무나 객관적인 방향 판단·보행 성공을 검증한 연구는 아니다.

### 22.3 지형 이미지 해석 오류에 관한 보충 문헌

Çöltekin, Biland (2019; 온라인 최초 공개 2018). Comparing the terrain reversal effect in satellite images and in shaded relief maps: an examination of the effects of color and texture on 3D shape perception from shading. *International Journal of Digital Earth*, 12(4), 442–459. [출판사 원문](https://doi.org/10.1080/17538947.2018.1447030).

27명이 33개 장소의 음영기복·회색 위성영상·컬러 위성영상에서 골짜기와 능선을 판단했다. 지형이 뒤집혀 보이기 쉬운 자극을 의도적으로 선정한 연구로, 영상의 색·텍스처가 지형 형상 해석과 관련되지만 오인식을 해소하지는 못했다. 결과의 낮은 정답률을 일반적인 위성영상이나 본 프로젝트의 오류율로 사용하지 않는다. 지형 인식을 만족도만으로 대체하지 않고 정답을 확인할 필요성을 뒷받침한다.

### 22.4 본 프로젝트에 적용할 때의 해석

이 문헌들은 건물·지형·이미지 세 요소를 본 프로젝트와 같은 1인칭 환경에서 하나씩 추가한 실험 결과를 제공하지 않는다. 관련 인식 과제와 비교 설계의 근거이며, 본 프로젝트의 개선 효과는 별도 측정 대상이다.

요소별 추가 효과를 분리하려면 동일한 장소·경로·시점·영상 길이에서 전체 표현과 특정 요소를 제외한 조건을 비교할 수 있다. 건물은 랜드마크 대응·방향 판단, 지형은 경사·고도 변화 판단, 이미지는 도로·녹지 구분 과제에 연결한다. 정답률·응답시간과 명확성·예상 유용성 설문을 함께 기록한다. 이는 실험 후보이며 아직 실행하지 않았다.

건물 표시를 끌 때 충돌·카메라 보정까지 달라지거나, 지형을 평탄화할 때 건물·경로가 부유하거나, 이미지가 없을 때 경로선까지 사라지는 조건은 요소의 시각 효과 외의 차이를 만든다. 자극 제작 시 이런 차이를 확인하고 통제한다. 지형 이미지에 건물 지붕이 포함되므로 건물 모델을 제외한 조건을 '건물 단서가 전혀 없는 조건'으로 부르지 않는다.

순차적으로 건물→지형→이미지를 추가한 비교는 그 순서에서의 추가 효과를 보여주며 각 요소의 독립 효과를 모두 분리하지는 못한다. 전체 표현에서 하나씩 제외하는 비교도 다른 요소가 존재하는 조건에서의 기여이며 모든 상호작용을 추정하지는 못한다. 현재 자료의 적용 가능 범위를 확인한 뒤 최종 조건을 정한다.
